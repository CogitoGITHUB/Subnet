* The blocked and parked work

** E-16b pm fetch -- BLOCKED
- *Purpose:* fetch and pin every declared package into the vault,
  without building, skipping ones already present, reporting
  new / already present / failed per package.
- *State:* the command is implemented and every single-add path is
  green. What fails is the SEQUENCE.
- *Root cause:* 3 or more sequential =vault-add= calls inside one
  shared test-runner process freeze with zero CPU and no live child
  processes (frozen 162s after the ff-b refmap). Six fresh adds
  standalone pass; one broken URL alone passes. All 155 children had
  already exited, so this is a pure-Racket block, not a slow git.
  The suspects are =child.lock=/=flock= plus a waiter-miss family in
  the run.rkt / vault child management. Repro: the full
  =backends/update.rkt= suite.
- *Decision:* =(DEFAULT: isolate the wedge in =core/vault-lock.rkt= and
  the run.rkt waiter, fix it, and keep E-16b BLOCKED until a 3-package
  fixture passes in one process.)=
  - (a) Hunt the wedge now and fix it. Recommended: E-16b/E-16c and
    the CLI fetch all wait on it, and it is the only thing between pm
    and a working =fetch=.
  - (b) Park it and ship single-add. Rejected: =pm fetch= on a real
    declaration with 2+ packages would still hang, which is the actual
    user path.
  - (c) Give each add its own process. Rejected as a workaround: it
    hides the bug and multiplies startup on a phone.

** E-16c parallel fetch -- BLOCKED
- *Purpose:* fetch with a concurrency limit (default 4), each waiting
  only on its own exit, one failure not stopping the others.
- *Blocked by:* E-16b. Parallel cannot go green while sequential
  multi-add wedges. Unattempted on purpose.
- *Decision:* =(DEFAULT: do not attempt until E-16b is green. Then
  serialize the vault write path per package and keep N=4.)=

** P-03 / P-04 jobs queue -- PARKED
- *Purpose:* a job queue for long or multi-package operations, with
  TEST-START before and TEST-END after every job so a stuck one is
  named.
- *Why parked:* two production defects. =job-start= rejects vault-wide
  jobs such as =op-gc= because =check-job-name= demands a package name
  (jobs.rkt:109-113 via =datum->job=:221), so a gc job can never be
  enqueued. And =job-cancel= opens =job-held.fifo= read-write and never
  closes it, which leaks a descriptor per cancel.
- *Decision:* =(DEFAULT: keep it parked and state plainly that pm
  v1 does NOT use the job queue.)=
  - (a) Keep parked, no jobs in v1. Recommended. The narration of D-036
    makes a hung operation visible in the feed without a queue; a
    queue would add a second way to be stuck.
  - (b) Fix both defects and wire apply through jobs. Deferred: it is
    real work for a problem v1 does not have.

* Phase G: the structural spine
All twelve are declared in D-038. The ones that genuinely need an
owner decision:

** G-01 dependency resolution and path conflicts
- *Question:* when two packages claim one path, does pm fail, or is
  there a declared merge policy?
- *Options:* (a) fail at plan time, always; (b) a merge policy
  expressed in the spec; (c) last-wins with a warning.
- *Recommendation:* (a) fail at plan time. Merging needs spec syntax
  and a user model; last-wins silently overwrites, which is the thing
  a package manager exists to prevent.
- *Default:* =(DEFAULT: fail at plan time with kind activate, naming
  both packages. G-02 through G-12 depend on this.)=

** G-05 generation GC policy
- *Question:* how many generations are kept, and can a generation a
  profile link points at be pruned?
- *Recommendation:* keep the last 5, never delete one a hold names,
  and never delete the one the profile link currently points at.
- *Default:* =(DEFAULT: last 5; holds and the live link are absolute.)=

** G-09 build isolation policy
- *Question:* is the network available during a build, and is the
  environment scrubbed?
- *Options:* (a) no network, scrubbed env; (b) network available,
  scrubbed env; (c) undefined.
- *Recommendation:* (a). Same-user, no chroot and no daemon is already
  decided; "undefined" is the hole, because a build step that fetches
  is unverified by construction.
- *Default:* =(DEFAULT: no network during build, scrubbed environment,
  stated in build.rkt and enforced.)=

#+TITLE: The modes, the tabs, the mode line, and one window for the tm and the editor
# One job: how the multiplexer is driven like the text editor — with modes, with
# tabs, with a mode line that says where the owner stands — and how one window
# size reaches both the shell panes and the editor panes at the same time.
# Status: written 2026-10-21 from the owner's request; this is the plan, the
# code lands with the items it depends on.

* What the owner asked
# the owner's words, in one line, and the shape it takes here.
  - The tm must be MODAL, with modes, like the text editor, so it is easy to
    use: the keys mean one thing in one mode and another thing in another.
  - The tm must have TABS and a MODE LINE: a tab bar that says which tab is
    open, and a line that says which mode the owner is in.
  - The owner must be able to control the WINDOW in the tm AND in the text
    editor IN SYNC: one window, one size, and what the shell draws is what
    the editor draws.

* The modes
# the smallest true statement: a mode says whose keys these are.
  - NORMAL is the multiplexer's own. The keys are the multiplexer's: the
    movement between panes and tabs, the opening of a pane, the opening of
    the agent pane, the modes themselves.
  - INSERT is the pane's own. Every key goes to the focused pane's program
    as it is typed — the shell, or the editor — exactly as it would without
    the multiplexer in the way.
  - COMMAND is a line at the bottom: the owner types a command, and the
    multiplexer runs it. It ends on Enter, and Escape leaves it.
  - The mode is a state the client holds, not a mode the pane's program
    knows about: the pane's program is never told that a multiplexer exists
    (rule 07: the program never learns which program answers).

* The keys, per mode
# the table is the truth; the mode line shows it.
  - From NORMAL: i enters INSERT, : enters COMMAND, the reserved prefix
    (Ctrl-b) is the escape hatch that works in any mode, and the arrow keys
    move between the panes of the current tab.
  - From INSERT: Escape returns to NORMAL, and every other key belongs to
    the pane's program.
  - From COMMAND: the words are the multiplexer's (=:tab new=, =:pane new=,
    =:mode=, =:q=), and Enter runs the one that is written.

* The tabs
# a tab is a set of panes; the session holds the tabs; the owner walks them.
  - A TAB is a set of panes of one session. The session holds the tabs in
    order, and the state record names them, so a reader (a person or an
    agent) knows the whole shape without guessing.
  - The layout file says which tab a pane belongs to, so a work layout that
    is restored on the phone comes back with its tabs.
  - The keys: the tab bar at the top names the tabs, the focused one is
    marked, and the owner moves between the tabs with the reserved prefix
    (Ctrl-b and then n or p) or with the mouse in the mode line.
  - A tab is the client's window onto the panes: the panes of the other
    tabs stay held by the holder and keep running (rule 01).

* The mode line
# one line at the bottom that says where the owner stands.
  - It shows: the MODE (NORMAL, INSERT, COMMAND), the current TAB, the
    focused PANE, the size of the window, and the keys that are free right
    now. Nothing else — the line is one line.
  - It is drawn by the client from what the holder says, so it never lies
    about the session: the tab names, the pane names and the sizes all come
    from the holder's state record.

* One window for the tm and the editor
# the answer to "in sync", and it is one sentence.
  - THE TM OWNS THE WINDOW. The terminal's size is the session's size, and
    the session tells EVERY pane that same size — the shell panes and the
    editor panes alike — and then tells every program to redraw (SIGWINCH).
  - So an editor in a pane and a shell in a pane are the same size at the
    same moment: there is one window, and the panes split it by their
    weights.
  - When the owner resizes the terminal, the client notices the new size and
    sends it to the holder, which resizes every pane and tells every program
    to redraw. The editor and the shell move together, not one after the
    other.
  - The layout's weights decide the split; the holder holds the sizes, so a
    client that ends leaves the panes sized as they were.

* What it must not do
# the refusals, each with the rule it refuses by.
  - No hidden mode: the mode is always on the mode line, and the owner can
    always see which mode the keys belong to.
  - No timers: the screen redraws on an event — a record arrived, a key was
    pressed, the window changed — and never on a clock (rule 04).
  - No key stolen from the pane: in INSERT the pane's program gets every
    key it would have got; the reserved prefix is the only exception, and
    it is the multiplexer's own (rule 06).
  - No mouse required: every command has a key (rule 13).

* The proof
# what must hold before this is called done, in the order it is seen.
  1. The owner opens the tm and the mode line says NORMAL.
  2. The owner presses i, and the mode line says INSERT; the keys now go to
     the focused pane's program, and the shell answers.
  3. The owner presses Escape, and the mode line says NORMAL again.
  4. The owner makes a tab, and the tab bar shows both tabs, with the new
     one marked; the panes of the other tab are still held.
  5. The owner resizes the terminal, and the shell pane and the editor pane
     are the same size at the same moment.

* What it depends on
# the items it cannot land before, by their numbers in the TODO.
  - The panes and the layout file (item 5): a pane must exist before a tab
    can hold one.
  - The key routing with the reserved prefix (item 6): the modes are the
    key routing.
  - The drawing of the panes on one terminal (item 5): the tab bar and the
    mode line are drawn on it.
  - The agent opens here (item 9): the key that opens the agent pane is one
    of NORMAL's keys.

* What the phone has to show first
# what is measured here and what waits for the laptop.
  - Here: the modes, the tab bar, the mode line, and one resize reaching
    both a shell pane and a second pane that runs a program which draws
    (a plain program, not the whole editor, so the proof is about the
    multiplexer and not about the phone's memory).
  - The full editor in a pane, in sync with the shell next to it, is a
    laptop question; it is measured when it is tried, and what the phone
    cannot do is written down in =../WHEN-ON-LAPTOP.org= the moment it
    shows up.

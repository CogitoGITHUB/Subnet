#+TITLE: The agent opens here — the key that carries the context with it
# One job: how one key in the multiplexer opens OpenCode with the context of
# the pane the owner is standing in, so nothing is copied and pasted by hand
# Status: written 2026-10-21 from the owner's request; this is the plan, the
# code lands with the items it depends on.

* What the owner asked
# the owner's words, in one line, and the shape it takes here.
  - In the tm, one key opens OpenCode and gives it the context from here:
    the shell output and the pane. The owner wants to move faster without
    copying the shell or the pane by hand.

* What it is
# the smallest true statement of the thing, before the details.
  - A key in the focused pane opens an AGENT PANE beside it, with a context
    bundle attached: what the pane's shell said, which shell it is, where it
    runs, and why the owner asked.
  - The key is the multiplexer's own. It lives in the reserved prefix
    (=../contract/key-routing.org=, D-005), so a key that belongs to a
    pane's own program still reaches that program first.
  - The bundle is the shared shape (=../contract/context-bundle-format.org=):
    selection (the output), file (none), position (none), notation address
    (none), why (never blank), origin (the multiplexer, this project), and
    target (the named agent — OpenCode — never inferred).

* Where the context comes from
# why this is cheap: the holder already holds the output.
  - The holder's session log holds every byte the shell wrote, one record
    per line, flushed per record. The context of a pane is the tail of that
    pane's log.
  - So the key never scrapes the screen and never copies text by hand: it
    asks the holder for the pane's records and sends them as the bundle's
    selection. The agent reads what the log holds.
  - The bundle passes the redaction seam: an agent receives text and
    pointers, never credentials.

* The shape
# the placement is data, and the tm's own shape is the pane beside.
  - A new pane beside the current one, running the agent. The pane's
    identity, the layout and the placement are data, so the same thing can
    later be a floating panel or a placeable piece without new code.
  - The agent pane is a pane like any other: it is held by the holder, so it
    outlives the screen that watched it, exactly like a shell pane.

* What it must not do
# the refusals, each with the rule it refuses by.
  - No copy and paste by hand: the context travels from the holder to the
    agent without the owner touching the text (rule 01).
  - No agent-specific keys in the bundle: the adapter translates, and the
    program never learns which agent answers (rule 07).
  - No timers: the key waits on events, and the pane opens when the agent's
    program starts, not on a clock (rule 04).
  - No mouse required anywhere: the key is a key (rule 13).

* The proof
# what must hold before this is called done, in the order it is seen.
  1. The owner stands in a pane whose shell has said something, and presses
     the key.
  2. A new pane opens beside it with OpenCode in it.
  3. OpenCode's first message already holds that pane's recent output, and
     nothing was copied by hand.
  4. The send itself is a record: the session's log says what was sent, to
     whom, and why.
  5. The pane's own log keeps its own records: the agent's pane is held
     like any other pane.

* What it depends on
# the items it cannot land before, by their numbers in the TODO.
  - The panes and layouts (item 5): a pane must exist before another one
    can open beside it.
  - The key routing with the reserved prefix (item 6): the key must be the
    multiplexer's own and must not steal a pane program's key.
  - The agent surface (item 4, landed): the wire the key uses is the same
    wire an agent reads, and the tool that reads a session's records is
    already proved on the phone.
  - Select and send (item 8): the bundle is what travels, and that is where
    the bundle is built.

* What the phone has to show first
# what is measured here and what waits for the laptop, in the plan's own words.
  - Here: one pane, one agent pane, the context attached, and the send
    recorded — with a plain agent program, not the full OpenCode, so the
    proof is about the multiplexer and not about the phone's memory.
  - The full OpenCode in a second pane on this phone is a phone question,
    not a design one: it is measured when it is tried, and what the phone
    cannot do is written down in =../WHEN-ON-LAPTOP.org= the moment it
    shows up.

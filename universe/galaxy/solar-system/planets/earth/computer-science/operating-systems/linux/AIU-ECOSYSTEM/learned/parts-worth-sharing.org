** A neutral written contract, adoptable without reading PM's code
# The spec design document is the model for the contract directory.
- What PM does: a standalone document lays out the spec grammar, the closed build-step vocabulary, install forms, the activation decision (a profile forest with generations), the build environment honestly (no sandbox on this phone), the dependency phases, a validator table and exact error messages — written so another repo can adopt it from the document alone; real names and pins appear only where pasted output proves them.
- The rule: a contract is a text another project can implement against, complete enough that its authors never need the implementer's code.
- Verdict: REUSE — this is the class of document the contract directory must become.
- Read at: docs/SPEC-NEUTRAL.org.

** One machine surface, read by every consumer
# The JSON documents are the only integration point anyone needs.
- What PM does: one object per invocation on one line, fixed key order, every operand a string, read by the CLI's human surfaces, the MCP server, the skill, the plugin and television alike.
- The rule: new consumers must never require new output paths; they read the one shape.
- Verdict: REUSE.
- Read at: docs/API.org; docs/HANDOFF-PROFILE-COMMANDS.org (surfaces section).

** The event narration and the wait door
# Every operation narrates completely and live; blocks announce themselves first.
- What PM does: every operation narrates itself completely and live, with no off-switch (D-036); blocking work gets a wait event before it and a done event after it, sharing one sequence counter so a wait with no match names the hang (D-041); the blocking primitives are enumerated and each goes through one door; the change followed a 41-minute hang whose feed had gone silent after its last event.
- The rule: a feed that stops mid-story is worse than no feed, so the thing that blocks must say so before it blocks.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-036 and D-041.

** The error type, the four answers, the frozen exit codes
# Failures are a surface with a shape, a home and samples.
- What PM does: WHAT, WHERE, WHY, NEXT; one exception type with kinds in one module; exit codes frozen in a table; each error kind has a test and a sample document.
- The rule: error output is a promised interface, so it is designed, tested and documented like one.
- Verdict: REUSE.
- Read at: 0.FOUNDATION.org section 6; docs/ERRORS.org (samples).

** The gate as a pattern, not a script to copy
# Sixteen stages, one verdict, and it proves itself by failing on purpose.
- What PM does: one gate script runs text lint, compile, the test suite, a paren check, domain lints (one printer, observability, security), an informational interpreter report and more; a changed-files mode exists for between-items runs; a stages variable can run a subset; and the gate is proved by a fixture that makes it fail non-zero.
- The rule: every program gets its own gate with the same anatomy — a failing fixture, stages that name themselves, and a fast subset that cannot silently skip the deciding stage.
- Verdict: ADAPT.
- Read at: gate/check.nu.

** The paren check that names the file and the line
# An unclosed form is reported at its opening line, not at the end of the file.
- What PM does: a small checker reads every named source file and reports the exact file and line of the first malformed form; it exists because the language runtime reports where reading stopped — the end of the file — which once sent someone deleting blind lines.
- The rule: when a tool's error message points at the wrong place, write the small checker that points at the right one.
- Verdict: REUSE.
- Read at: gate/read-check.rkt header; docs/LESSONS.org.

** The shared-process test runner as a portable asset
# One process, explicit failure detection, nothing skipped silently.
- What PM does: all test files run in one process and one namespace; failures are detected by diffing the framework's counters around each file, so a failure cannot read as a pass; a file with nothing to run is reported as NO-TESTS rather than skipped; per-file isolation covers the working directory, the environment and the exit handler.
- The rule: the test harness is infrastructure other programs can carry, as long as the principle travels: never trust silence, never skip invisibly.
- Verdict: REUSE.
- Read at: gate/test-runner.rkt.

** Trust tiers and the visible escape hatch
# Data is read; code is only what the user owns; the one raw step is highlighted.
- What PM does: two trust tiers with code never loaded from fetched content; a closed step vocabulary; the single explicit run step is highlighted in plan output and warns in strict mode; dry-run is the default for specs from outside the repo.
- The rule: the security boundary is data versus code, and the escape hatch is visible by construction.
- Verdict: REUSE.
- Read at: 0.FOUNDATION.org section 8.

** Pins, the vault, and fetch-once
# Sources are cloned fully, pinned exactly, verified before use, never fetched at install time.
- What PM does: git only, full clones always so the source survives upstream; exact commit ids in the lockfile; private pinned refs per commit; export at the pin from the vault, never the network; install reads the vault.
- The rule: network access is one pipeline stage, and everything after it consumes verified local state.
- Verdict: REUSE.
- Read at: 0.FOUNDATION.org S-4 and S-5; plan/DECISIONS.org D-006, D-011, D-012.

** AI surfaces ship together with the CLI
# One JSON shape; read is free; every mutation needs the human token.
- What PM does: the MCP server and the OpenCode plugin are shipped; the skill is owed; read is free, and every state-changing tool needs the human confirmation token; without confirmation, apply prints the plan and changes nothing; never auto-apply (D-040); the ecosystem rule is the same: engine, MCP server, skill and plugin ship together.
- The rule: an AI surface is part of the program, not an add-on, and it inherits the confirmation gate unchanged.
- Verdict: REUSE.
- Read at: plan/OPEN-DECISIONS.org (E-27, E-28, V-5); plan/DECISIONS.org D-040.

** The append-only logs
# Decisions newest-first with rule IDs; lessons with root cause and new rule.
- What PM does: one decision log, append-only, newest first, each entry naming the rules it touches; one lessons log, append-only, each entry stating what happened, the root cause and the new rule.
- The rule: the two logs are how a program explains itself to its future self, and both are cheap only if started on day one.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org header; docs/LESSONS.org header.

** What not to share: PM's code
# The four programs share a contract, not a runtime.
- What PM does: PM is a separate program with its own process, store and profile; it offers documents, not libraries.
- The rule: four packages sharing only a versioned written contract, separate programs, crash isolation — PM already demonstrates the working version of this stance.
- Verdict: DO NOT REPEAT — do not repeat the temptation to require PM (or each other) at runtime; copy shapes into each program's own implementation and let the contract be the only coupling.
- Read at: 0.FOUNDATION.org A-1 (one-way dependencies, interfaces through structs of functions); the four-programs decision recorded at the ecosystem level.

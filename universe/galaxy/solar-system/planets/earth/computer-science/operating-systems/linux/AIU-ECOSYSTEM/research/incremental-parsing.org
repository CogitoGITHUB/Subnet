* What it is
# the project, its language, its health, and who maintains it.
  Two parser systems built for editors. Tree-sitter (tree-sitter.github.io;
  repo MIT, 27.2k stars, last push 2026-10-16): "a parser generator tool and
  an incremental parsing library" that builds a concrete syntax tree and
  efficiently updates it as the source file is edited, aiming to be general
  enough for any programming language. Lezer (lezer.codemirror.net guide):
  a JavaScript parser system — grammars compile offline into parse tables
  (a generator tool), a small runtime applies them; its trees are concrete
  rather than abstract, it re-parses efficiently given the old tree when
  text changed slightly, and error recovery is built in. The Lezer guide
  credits Wagner and Graham's work on incremental parsing.

* What transfers
# one line per mechanism worth borrowing, each with the reason it fits a program here.
  - Incremental reparse is non-negotiable for a live editor: full reparses
    per keystroke do not scale; design the notation's parser for edits.
  - Error recovery: intermediate broken text must still yield a usable tree,
    because that is what editing looks like.
  - Build-time/runtime split: tables generated offline, a small runtime
    shipped — fits a phone (no code generation at startup).
  - Concrete trees serve editing directly (highlighting, structure) — one
    tree, not a second model.
  - The academic lineage (Wagner and Graham) is documented; we can follow it
    when we get there.

* What to avoid
# one line per mechanism we deliberately do not take, with the reason. No code.
  - Committing to a grammar toolchain before the notation's grammar exists.
  - A JavaScript parser host (Lezer's world) — lesson source only; our
    programs are Rust.

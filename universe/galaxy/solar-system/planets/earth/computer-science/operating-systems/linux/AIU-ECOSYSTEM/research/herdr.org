* What it is
# the project, its language, its health, and who maintains it.
  herdr (github.com/herdrdev/herdr, herdr.dev) is a terminal multiplexer in
  Rust with the tagline "the runtime your coding agents live on". Agents are
  first-class: Claude Code, Codex, Cursor, OpenCode, Grok and others run
  unmodified in panes and tabs, each in its own PTY, and every pane is
  marked working, blocked, or idle. Active: 44k stars on GitHub, last push
  2026-10-15. One Rust binary, no Electron.

* What transfers
# one line per mechanism worth borrowing, each with the reason it fits a program here.
  - Detach without stopping work: a background server keeps terminals alive
    when the client closes, and after a restart it restores the saved layout
    and resumes supported agent sessions, stating plainly that the original
    processes do not survive. The honesty is part of the design.
  - Status per pane: working, blocked, or idle, so an agent that needs an
    answer is visible without hunting. This is the state model our terminal
    multiplexer wants for its own agents.
  - Agent-native control: agents drive herdr through a CLI and socket API —
    spawn panes, prompt each other, wait until another agent is genuinely
    blocked. Our programs need the same kind of control seam.
  - Several machines, one window: local work and saved remote machines in
    one list, with independent reconnects.
  - Keyboard and mouse both first-class: tmux-style prefix keys and direct
    click, drag, split; pick per moment, not per tool.

* What to avoid
# one line per mechanism we deliberately do not take, with the reason. No code.
  - The plugin marketplace: another extension runtime and catalog is weight
    we do not need; our extension surfaces are MCP and skills.
  - N named agent integrations: we keep one agent-neutral boundary
    (OpenCode and Hermes behind pinned adapters), not a growing list.

#+TITLE: Keyboard: Racket vs Rust
# One job: what becomes Racket config and what stays in the Rust input engine: the exact seam
# Status: filled 2026-10-16 from Cyberdeck-Emacs, read-only; not yet reviewed.

* What becomes Racket config
# the keyboard layer parts that are description and meaning: what exists, what it shows, keymaps, commands, rules.
  - The state list: names, markers, cursor shapes, and whether a state is auto
    or manual.
  - Activation predicates and the precedence order — meaning, not speed.
  - Key tables: state to key to command, shared binding sets, leader tree and
    menu declarations with their groups, titles and sticky flags.
  - Command wiring: which command id a key names, and the declared routes that
    decide where keys go between multiplexer, editor and panes (rule 13's
    split).
  - Validation rules and creators: duplicate keys, unbound commands, dead
    states, evaluation order; new-state and new-leader skeletons.
  - What the model means: which state a buffer should wake in, which keys are
    reserved at the routing level.

* What stays in Rust
# the parts on the hot path: input, drawing, layout.
  - Key-event decode: raw input, escape sequences, terminal handling, and the
    blocking read that decides whether a second key follows.
  - Timing: chord delay, ESC/Meta disambiguation, repeat-last bookkeeping at
    dispatch.
  - Lookup: resolving a key event against the active state's compiled tables,
    including the routing table.
  - Drawing: menu surfaces, selection overlays, highlight overlays, cursor
    shapes, the state name in the modeline, relative line numbers.
  - The undo-grouping entry points at the editor core (what belongs in a group
    is config).

* The exact seam
# where the two meet, named precisely; this is the seam rule 09 demands.
  - The seam is the resolved key event: Rust produces a key event (code,
    modifiers, timing) and consumes command ids; Racket owns the
    state-to-key-to-command tables and the activation predicates.
  - Concretely: Rust decodes the event, consults the routing table and the
    current state's table, runs the command id; Racket never sees raw events,
    and Rust holds no key literals and no predicate logic.
  - Predicates run at buffer activation, not per key, so they stay on the
    config side; Rust only exposes the facts they read (read-only, major mode,
    region active).
  - The baked binary carries the tables as data; work mode rebuilds them from
    source and never touches the decode path.

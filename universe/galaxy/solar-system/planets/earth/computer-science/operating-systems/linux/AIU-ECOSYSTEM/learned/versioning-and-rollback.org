#+TITLE: Versioning and rollback in the package manager
# One job: how PM versions and rolls back, because adapters and the contract must reuse it
# Status: filled 2026-10-16 from =AIU-OS/AIU-PM=, read-only; every item names the PM path it was read from.

* How to read this file
# Verdict key: REUSE carries, ADAPT re-shapes, DO NOT REPEAT did not survive.

  - The subject is profiles, generations and every promise made around a mutation.
  - The adapter packages will need exactly these promises: versioned, pinned, reversible.

** A profile is numbered generations; one atomic flip picks the live one
# Versions accumulate; a single symlink decides which one is real.
- What PM does: pm resolves, builds and installs into a profile — a numbered set of generations, with an atomic symlink flip choosing the live one; activate, rollback and remove are the commands that operate on a profile.
- The rule: installing never overwrites the previous state; it adds a generation and flips one link.
- Verdict: REUSE.
- Read at: docs/HANDOFF-PROFILE-COMMANDS.org.

** The current link insulates consumers
# One stable path per package; nothing outside the installer sees generations.
- What PM does: one current symlink per package; the loader points at current, so upgrades and rollbacks never touch it; manager state (lockfile, logs, cache) lives in a separate state directory, never with installed packages.
- The rule: consumers depend on one stable name; the version machinery stays behind it.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org (D-005 details).

** Fail closed: a failed or cancelled apply leaves the old current untouched
# Incompleteness is marked, the old state survives every failure path.
- What PM does: a prefix stays marked incomplete until its check passes; a failed or cancelled apply leaves the old current untouched; without confirmation, apply prints the full plan and exits having changed nothing; a state-changing tool call needs the human confirmation token.
- The rule: the failure paths are designed first, and none of them may consume the working version.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-040.

** Remove unlinks; pruning is a separate, explicit command
# The frequent operation is cheap and reversible; the destructive one is deliberate.
- What PM does: remove unlinks the package from the profile only — it touches no store directory and frees no disk; freeing disk is a separate explicit prune or clean command, never a side effect; generations are never pruned by age or a sweeper.
- The rule: never let the routine operation quietly destroy the thing that makes rollback possible.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-024 and D-015.

** Slots name the version streams
# Two incompatible majors coexist because the stream is part of the name.
- What PM does: a slot is a named version stream of a package; different slots install side by side; a profile holds at most one version per slot; update and hold work per slot, never per package name alone.
- The rule: version coexistence is solved by naming, not by renaming or by luck.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-023.

** Install identity is content, not a label
# Anything that changes the build changes the identity.
- What PM does: install identity is name plus slot plus version plus an input hash; the hash covers the resolved flags and the identity of every dependency, so changing a flag or a dependency cascades into a different identity and therefore a different store directory; the flags actually used are recorded in the lockfile, so a profile cannot claim to hold a build it did not make.
- The rule: identity is computed from what was really built, never asserted.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-023 and D-022.

** The spine around mutations: verify, ledger, provenance
# The machinery that makes remove and rollback honest.
- What PM does: verify is its own stage between fetch and apply, for both source and artifact integrity; a path ownership ledger exists so remove and rollback cannot strand or overwrite; provenance on every generation ties the event feed to the ledger; apply is idempotent and SKIPs rather than reinstalls.
- The rule: rollback is only real if something knows every path a generation owns.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-038.

** Generation GC can refuse: never a held generation
# The keep policy has a floor it may not cross.
- What PM does: the generation GC policy keeps the last N generations and never a held one.
- The rule: a collection policy that cannot refuse a keep request is a delete policy.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-038.

** Generated state lives outside the tree, from one seam
# Sources in the repo; everything produced elsewhere, named once.
- What PM does: everything generated goes outside the repository tree — caches, targets and profiles in the XDG directories, the vault beside the state directory; all roots come from one scope module; each scope has its own store, lock, manifest and profile, with no sharing.
- The rule: the tree holds sources only, and generated state has exactly one place that names where it lives.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-016 and D-029; gate/env.nu.

** Dev mode reuses the whole pipeline
# A side channel for live checkouts, kept out of the installed-state formats.
- What PM does: dev mode registers a local working checkout for iterating without commit and push cycles; the link record lives in its own state file, not in the spec, the manifest or the lockfile; build steps run unmodified with the checkout as source, and install places symlinks instead of copies; removal is its own command.
- The rule: development state is a defined side channel, never smuggled into the formats that describe real installs.
- Verdict: ADAPT — the pattern matters for the new programs once their own checkouts need live iteration; the mechanics are PM's.
- Read at: docs/DEV-MODE.org; plan/OPEN-DECISIONS.org (E-19 dev mode — done, one thing owed).

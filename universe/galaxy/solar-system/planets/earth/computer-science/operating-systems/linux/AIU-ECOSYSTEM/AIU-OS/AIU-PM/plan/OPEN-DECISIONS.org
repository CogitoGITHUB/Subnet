* BLOCKED, platform: the parent cannot hold a fifo writer open
:PROPERTIES:
:END:

The =run-command= fifo strand is FIXED at its cause: =#:cwd= is now
validated in =spawn-prelude= before anything is created or spawned, so a
nonexistent directory raises a named =exn:fail:pm= instead of letting the
child die in =chdir= before the wrapper's first act. That was the whole
of the measured hang (package-manager/src/git/git-repo.rkt, 7+ minutes on a =git-has-commit?=
against a =demo.git= that was never created).

What is NOT done is the belt-and-braces part: having the PARENT hold a
fifo write end so the reader can never lack a writer. Racket 9.3 cannot
express it. Probed in a scratch file, all three file-open functions:

| call | result on an existing fifo |
|------+-----------------------------|
| =open-output-file= (=#:exists 'error=) | raises "file exists" |
| =open-output-file= (truncate/replace, update, append) | RETURNS AT ONCE, never blocks |
| =open-input-output-file= | raises "file exists" |

=open-file-output= does not exist in this Racket. So there is no call
that BLOCKS on a fifo write end, which is precisely what a holder needs.
The holder was written, measured not to work, and removed rather than
shipped with a comment claiming a guarantee the code did not provide.

Consequence, stated plainly: if a child dies before the wrapper's first
act for some reason other than a bad =#:cwd=, the reader still parks in
=open()= on the fifo read end with nothing to wake it. The wait on the
child now goes through the wait door (=wait-for=), so such a block is
narrated rather than silent, and the cwd guard removes the one path
observed in practice.

- *Recorded as ACCEPTED-MITIGATED* at the run.rkt split (MOVE-ORDER step
  4). The cause is fixed and measured; the belt-and-braces holder is
  impossible in Racket 9.3 and was removed rather than shipped
  pretending. It is not a live bug and it is not silently dropped.

* The backup's two open questions, decided

** Where the backup repo lives
- *Question:* a new XDG config root, or a sibling of the vault?
- *Options:* (a) new XDG root, =<state>/backup-repo=; (b) sibling of
  the vault, so it sits next to the thing it backs up; (c) inside the
  vault, as a subdirectory.
- *Recommendation:* (b). The vault is the one location that is already
  git-owned, already a sibling of the store, and already on the same
  volume as the state it backs up. A second XDG root adds a place to
  configure for no gain.
- *(DEFAULT: (b), the backup repo is a sibling of the vault under the
  state root, overridable by =PM_BACKUP_PATH= exactly as the vault is
  overridable by =PM_VAULT=. Not configurable means SKIP, never error.)*
- *Rejected:* (c). Putting a git repo inside another git repo is how
  you get a backup that silently never gets pushed, because the outer
  repo treats it as an ordinary directory.

** Does a push retry block the caller
- *Question:* block in the wait door, or run detached and record the
  result?
- *Options:* (a) block, narrated; (b) detached, with a result record;
  (c) neither, fail the fetch.
- *Recommendation:* (a). D-015 forbids timers, and a detached push needs
  somewhere to record its result and something to wake it; that is a
  second queue, and =P-03= already showed that a queue is a second way

* Multi-user declarations and config -- DECIDED
Eight questions answered by the owner in one pass. Each is now stated in
the design it belongs to, and removed from that design's open list. The
designs are =plan/FEATURE-users.org= and
=plan/FEATURE-config-and-completions.org=.

** User identity -- DECIDED
- *Decision:* =(DEFAULT: a user is a name AND a uid. The name is the key
  the file is found by; the uid is recorded in the user file and checked
  at apply. A mismatch is a named refusal, not a warning.)=
  Two halves of one identity: the name says which declaration, the uid
  says whose hands are on the machine.

** user.rktd names packages, the lockfile pins them -- DECIDED
- *Decision:* =(DEFAULT: the user declaration lists package NAMES only; the
  lockfile is the only thing that pins a version.)= The split in one
  sentence: the user file says WHICH packages this person wants, and the
  lockfile says WHICH version of each.

** Applying another user takes both gates -- DECIDED
- *Decision:* =(DEFAULT: =pm user apply= for a different user requires
  =--confirm= AND the confirmation token; applying to yourself requires
  =--confirm= only.)= Touching your own machine is one gate; touching
  someone else's is two.

** System-forced packages and the hold budget -- DECIDED
- *Decision:* =(DEFAULT: a system-forced package does NOT count toward a
  user's hold budget.)= It is forced, so counting it would let forced
  packages crowd out the user's own pins.

** No per-user store quota -- DECIDED
- *Decision:* =(DEFAULT: none today. The size limit in the user file
  applies to the backup only.)= Revisit if the shared store grows.

** pm config is read-only forever -- DECIDED
- *Decision:* =(DEFAULT: =pm config= never writes. Every change goes
  through the user file or through =pm add= / =pm drop=, both gated by
  =--confirm=.)= One place to edit a setting, and it is a file a human
  can read.

** Completions cover three things -- DECIDED
- *Decision:* =(DEFAULT: verbs, flags, and directory operands. Nothing
  else.)= No package names and no values, so completion never guesses.

** pm never installs its completions -- DECIDED
- *Decision:* =(DEFAULT: pm prints or copies the completion files and
  never writes outside its state root. README.md documents the one manual
  placement step.)= Same law as the backup path decision: pm does not
  write where it does not own.

* Deliberately not planned
Three things README.md lists under "Deliberately not planned". They are
recorded here because a refusal without a recorded reason is indistinguishable
from an oversight: the reader must be able to ask why, and get an answer.

** Install hooks -- NOT PLANNED
- *Decision:* =(DEFAULT: pm never runs unapproved code at install time.)=
  Arbitrary code run at install time would break the fail-closed rule: a
  hook could change the machine after the plan was approved. pm will not
  grow a place to run unapproved code.

** Services -- NOT PLANNED
- *Decision:* =(DEFAULT: pm does not run or supervise daemons.)= Running
  and supervising services is a different job with a different failure
  model, and out of scope for what pm does.

** Vulnerability audit -- NOT PLANNED
- *Decision:* =(DEFAULT: pm will not claim a package is safe.)= An audit
  needs an advisory source pm does not have. If one is chosen this is
  revisited; until then there is nothing to report and no way to claim
  safety.

* Confirmation token -- DECIDED (owner, 2026-10-16)
Audit findings 1 and 2. The token was the compile-time constant
"pm-confirm-0001", so holding a public string authorised disk mutation. It
is now a per-session secret, spent by its first use and bound to the plan
it approved.

** Where the secret comes from
- *Decision:* =(DEFAULT: 32 bytes from the OS CSPRNG, hex-encoded. Never a
  timestamp, never a counter, never anything reproducible.)= A token a
  reader could guess is not a secret.

** Single use
- *Decision:* =(DEFAULT: the first state-changing call a token approves
  SPENDS it, and every later call with that same token refuses.)= Refusal
  name: "confirmation token already used". One approval, one call.

** Bound to a plan
- *Decision:* =(DEFAULT: a token is issued against a digest of the plan it
  approves, and a call whose plan digest differs refuses under its own
  name, "confirmation token is for a different plan".)= Approval of one
  thing is never approval of another, however similar the two look.

** Expiry is by use and by session end, never by clock
- *Decision:* =(DEFAULT: no timer and no TTL. A token dies when it is spent
  or when its session ends.)= D-015 forbids timers outright, and a
  wall-clock expiry is a second thing that can fail silently.

** The request is narrated
- *Decision:* =(DEFAULT: asking for a token emits a WAIT event naming the
  command and the plan digest being authorised.)= README group 3's law: if
  it can block a human, it says so before it blocks.

** One list, two surfaces
- *Decision:* =(DEFAULT: state-changing? is the ONLY list of commands
  needing human confirmation, and BOTH the CLI and MCP consult it.)= The
  CLI kept a hand-written per-command list, so the two surfaces could drift
  apart with nothing noticing. One list, one gate, one test that they agree.

** One list, and a deliberate asymmetry
- *Decision:* =(DEFAULT: the CLI acts directly; MCP requires the token. The
  asymmetry is DELIBERATE.)= A human at a terminal IS the confirmation on the
  CLI: there is nobody else to ask, and =--confirm= exists where a preview
  earns its keep (=pm apply=). MCP cannot assume that, because the caller is an
  agent and an agent is not a human. So no gate is added to =fetch=, =update=,
  =activate=, =rollback=, =remove= or =hold=: =README.md= and =docs/API.org=
  document those verbs as acting directly, and inventing a gate for them would
  be an authorisation change nobody asked for. What the two surfaces SHARE is
  the named set =state-changing?= and nothing else: one list, no second
  hand-written copy, and a test that both surfaces read that one list.

** The suite was already red before this work
- *Finding:* =(2026-10-16, measured before the token change: 73 files, 939
  checks, 17 FAILED.)= It was never hung: it ran 566s and its output grew
  throughout, 73 of 73 files started and finished. The failures sit in files
  this work never touched and are mostly environmental -- fixtures missing
  under =/var/tmp=, and cwd-relative paths that do not resolve -- plus ONE
  real defect: =git-clone-mirror= breaks its own contract at
  =git-repo.rkt:297=, returning a procedure where =void?= is promised, which
  is what fails =apply.rkt= and =local-perform.rkt=. So the gate cannot be
  called green until that is fixed, and this line exists so "the suite was
  red first" is never later mistaken for damage done here. Caveat, stated
  rather than hidden: that run overlapped the edits to =security.rkt= and
  =mcp-tools.rkt=, so it is a strong signal rather than a proof.

* The one-way area law does not match the tree -- FOUND, DECISION NEEDED
:PROPERTIES:
:ID: oneway-law-gap
:END:

=gate/one-way-dependency-lint.nu= transcribes ARCHITECTURE.org's area
table and checks every cross-area =require= under =package-manager/src/=.
Written as step 18 and run on the tree of 2026-10-17, it reported 34
crossings that the doc says cannot exist, in 14 area-pairs:

- =spec/= and =git/= require each other. That is a cycle, not a ranking,
  and no table of one-way edges can be satisfied by a cycle.
- Ten modules in =install/=, =machine/=, =spec/=, =store/= and =queue/=
  reach up into =entry/=, which the doc calls the ceiling.
- =git/= requires =security/=; =machine/= requires =git/= and =spec/=;
  =narration/= requires =machine/=; =store/= requires =install/=,
  =machine/= and =queue/=.

The stage is wired and green because the debt is enumerated in the
script's =KNOWN_PAIRS=: those edges print on every run as "known unpaid
edges", and a NEW crossing still fails with =file:line=. So the law is
enforceable for anything new from today, and the existing gap is visible
instead of implied.

What is NOT done, and is now a decision for the owner -- make the tree
match the doc, or the doc match the tree:

1. Move the modules so the ranking holds. Breaks the spec/git cycle and
   gives =entry/version.rkt= a home below the ceiling. A real refactor,
   worth its own step; this is the only option that keeps the law a law.
2. Correct ARCHITECTURE.org to the shape the tree actually has. Honest,
   cheap, and retires a rule that three phases of work already ignored.

Recommend 1, in a step of its own. It is not folded into step 18 because
a 34-edge dependency refactor is not a step's worth of work, and because
the lint already stops the gap getting any wider.

Recorded rather than fixed: the alternative -- quietly widening the table
until it matched -- would have destroyed the only copy of the intended
shape, which is the thing worth keeping.

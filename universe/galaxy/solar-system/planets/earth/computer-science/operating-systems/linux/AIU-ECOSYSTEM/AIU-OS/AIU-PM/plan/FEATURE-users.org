#+TITLE: FEATURE users — one store, many users, one declaration each
#+AUTHOR: Shape

Design only. No code lands with this file.

* Goal
Let one machine carry a package set per person without letting one person's
work disturb another's. The store is shared and content-addressed, so a
build exists once no matter how many users asked for it; everything that
records intent — profile, generations, holds, lock, mirror settings — is
per user. Two people on one machine get the same bytes and separate
histories.

* Model
- IDENTITY: a user is a name AND a uid. The name is the key the file is
  found by; the uid is recorded in the user file and checked at apply.
  A mismatch is a named refusal, not a warning.
- SHARED: the store. Content-addressed, so one copy of each build serves
  every user. Also shared: the vault of git clones, which is history, not
  installation state.
- PER USER: the profile directory, its generations, its holds, its lockfile,
  its mirror settings, and its user declaration.
- Users NEVER share a profile. One user's rollback, gc or remove touches
  only that user's generations; it cannot repoint another user's link.
- One user's gc may reclaim shared store paths, but only after proving no
  other user's live or held generation still needs them (see Safety).

* User declaration file
One file per user. Name: =user.rktd=, in the =.rktd= s-expression
vocabulary the spec parser already reads, with its own top-level form so
the two never get confused:

  (user-declaration
    (format-version 1)
    (name "shape")
    (uid 1000)
    (profile "shape")
    (lock "pm.lock")
    (mirror (repo "mirror-repo") (remote "git@host:mirror.git")
            (size-limit 52428800))
    (packages lua guile))

It lives at =<state>/users/<name>/user.rktd=, beside that user's profile,
holds and lock, so one user's whole world is one directory. The split is
one sentence: the user file says WHICH packages this person wants, and the
lockfile says WHICH version of each.

Relation to the spec directory: the =.rktd= package specs stay exactly what
they are — the definition of a package, its source, its build and its
install forms. The user declaration never redefines a package; it CHOOSES
from the ones already declared, by name and version. =pm check= still
validates spec directories; =pm check-user= would validate this file under
the same rules, and a bad field raises kind =spec= like any other
declaration error.

* Layering
Today there is exactly one layer: the user declaration. The layer above it
is RESERVED, NOT BUILT.

Reserved name: =system.rktd=, root-owned, expected at =/etc/aiu-pm/= once
the parked system-declaration project (see =AIU-OS/system-declaration.md=,
phases S4 and S6) is approved. pm does not read it, does not write it, and
refuses to pretend it exists: until that project opens, this file is only a
name reserved so nothing else takes it.

Conflict rule for the day it is built:
- A setting a user states in their own declaration WINS over a system
  default. The user's machine profile, lock path and mirror settings are
  theirs.
- A package the system layer FORCES is present in every user's effective
  view and cannot be dropped by a user. =pm drop= refuses by name, citing
  the system layer, and the refusal is not overridable by =--confirm=.
- Everything else the system layer lists is a default the user may override.

* Commands
- =pm user list= — zero operands. Every user declaration found, with its
  profile and package count. Read-only.
- =pm user show NAME= — one operand. That user's declaration, and the
  effective view: which value each setting took and which layer it came
  from. Read-only.
- =pm user apply NAME [--confirm]= — one operand. Activates that user's
  declaration into their profile. Without =--confirm= it plans and changes
  nothing. For a user other than the caller it needs =--confirm= AND the
  confirmation token; applying to yourself needs =--confirm= only.
- =pm add NAME= / =pm drop NAME= — one operand, the package name. Rewrite
  the USER DECLARATION. Without =--confirm= the rewrite is printed as a
  diff and nothing is written.
- =pm config= — zero operands. Read-only view of effective settings and the
  layer each came from. Detailed in =FEATURE-config-and-completions.org=.

Reads: user declaration files, the spec directory, the per-user profile and
generations, the holds file, the lock.
Writes: the user declaration (=pm add=, =pm drop=) or that user's profile
generations (=pm user apply=) — both only under =--confirm=.

* Refusals, by name
- "needs --confirm": =pm add=, =pm drop=, =pm user apply= without the flag.
  They print the exact command to re-run and exit.
- "unknown user": no =user.rktd= for that name. The refusal names the
  directory searched.
- "uid mismatch": the uid recorded in the user file is not the uid the
  command runs as. It names both uids. A named refusal, never a warning.
- "unknown package": =pm add= names a package no spec declares.
- "system-forced package": =pm drop= against a forced package. Names the
  package and the system layer. =--confirm= does not override it.
- "not your profile": a user naming another user's profile in an apply,
  rollback, remove or gc. Names the profile and its owner.
- "user declaration invalid": a bad field, a wrong format version, or a
  package that no spec declares. Kind =spec=, with the file and field.
- "system layer not built": any attempt to point pm at =system.rktd= today.
  It refuses rather than ignoring the file.

* Safety
- GC ACROSS USERS. Before freeing any shared store path, gc builds the
  reachability set from EVERY user's profile: each user's live generation,
  each user's held generations, and each user's newest N. A store path is
  freed only when no user's set still reaches it. gc then narrates the count
  it consulted — "3 users, 9 live generations, 2 held, 4 paths freed" — so
  the human can see whose work was weighed. A user who cannot be read (a
  declaration unreadable) makes gc REFUSE for everyone rather than assume
  that user needs nothing.
- PERMISSIONS. One user cannot write another's profile. The check is a pure
  predicate in =security/=, asked before any write: does the caller's
  profile directory match the target's owner? The profile directory itself
  carries its owner's name; the shared store and vault are world-readable
  and only pm writes to them, never a person directly.
- Holds are per user, so a user holding a package protects it from EVERY
  user's gc, not only their own. That is the point of counting first.
- A system-forced package does not count toward a user's hold budget, so
  forced packages cannot crowd out the user's own pins.
- There is no per-user store quota. The size limit in the user file applies
  to the mirror only; revisit if the shared store grows.

* Mirror interaction
Two options, and a recommendation.
- Option A: one mirror repo per user, each with its own remote. Clean
  isolation; N remotes to configure, N credentials, and no single backup
  that shows what the machine as a whole looks like.
- Option B (RECOMMENDED): one shared mirror repo with per-user directories,
  =users/<name>/decl/= and =users/<name>/vendor/=. One remote, one push,
  one credential; the machine's full state is backed up in one place; and a
  user only ever writes their own directory, so isolation is pm's rule, not
  a hope about git's. Cost: the remote needs write access to many
  directories under one account, and a user who pushes must not be trusted
  to stay inside their directory — pm enforces that, and never relies on
  the remote for it.
Recommendation: Option B. The mirror is a backup and never an input to
install (see =plan/MIRROR-FEATURE.org=), so sharing the repo costs nothing
in correctness.

* Area
Following the one-way law in =plan/ARCHITECTURE.org=:
- =spec/user-declaration.rkt= — read and validate =user.rktd= (pure).
  spec/ is where declaration formats live.
- =spec/user-view.rkt= — the effective view: user file over system
  defaults, the conflict rule, the forced set (pure).
- =security/user-write.rkt= — the predicate "may this caller write this
  profile" (pure; security/ is policy, never effects).
- =install/user-gc.rkt= — gc reachability across every user's generations,
  beside the gc it extends.
- =entry/user-report.rkt= — the result documents for =pm user list/show=,
  =pm add/drop=, =pm user apply= and =pm config=.
Nothing below entry/ ever requires it; =errors/= requires nothing.

#+TITLE: export and import — a setup that can leave the machine
#+AUTHOR: Shape
# One job: portable bundles: =pm export= writes one, =pm import= reads
# it back on another machine. Status: planned only; nothing here is
# built, and no name here may be used by code until the register lists
# it (step 3). Source: =plan/FEATURE-export-import.org=.

* Purpose
- A machine can be set up today but never reproduced elsewhere: the
  declarations and sources exist, and no portable form of them does.
* Name and location
- names: =bundle-format=, =export-profile= and =import-profile= per the
  FEATURE
- code: =src/store/bundle-format.rkt=, =src/install/export-profile.rkt=,
  =src/install/import-profile.rkt=
- area and layer: =store= (8) owns the format; =install= (11) writes
  and reads profiles
- may require: as those areas already may
- may be required by: =entry=
* Public interface, in plain words
- export: one checksummed file naming the declarations and sources;
  import: verify first, refetch what it can, refuse what it cannot.
* What it must never do
- Never trust a bundle: verify before use; a mismatched checksum is a
  refusal by name.
- Never carry secrets: the same redaction rules as the feed.
* Tests
- =tests/store/= and =tests/install/=; one fixture: export, import on a
  clean root, same result.
* Docs it updates
- =plan/NAMING-REGISTER.org=; =plan/FEATURE-export-import.org= open
  questions.
* Depends on new components
- =binary-cache= shares the content-address shape: agree on it once,
  in either file, before both land.
* Build order
- =plan/MOVE-ORDER.org= step 24.

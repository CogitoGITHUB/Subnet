#+TITLE: Context-bundle senders
# One job: how PM sends a package, a plan or a failure to an agent as a context bundle
# Status: filled 2026-10-16; planned only, PM itself is not touched here.

* What PM must gain
# the capability in words; the exact PM files are named only after PM is read, until then say where to look later.
  - Three senders built on the one bundle shape (contract step 9): a
    package (name, slot, pin, where it came from), a plan (the resolved
    plan as a document), and a failure (WHAT, WHERE, WHY, NEXT — the four
    answers PM already promises).
  - Every bundle carries why it was sent and names its target; sends go
    through the AI link boundary (agents/ai-link-boundary.org) and the
    choosing rule — never an agent picked silently.

* Shape
# how the entry, surface or file looks from the outside. No code.
  - A bundle is a document: a header (who sends, why, what) plus
    references — paths into PM's own state and docs; a failure carries
    its error kind.
  - No secrets, ever: bundles pass the same redaction seam
    (agents/secrets-handling.org); an agent receives pointers, never
    credentials.
  - PM never learns which agent reads a bundle; the adapter handles that.

* Proof that it works
# the one check that shows this is done when the PM prompt runs.
  - A bundle built from a real failure is readable alone — a reader with
    no PM internals gets the four answers and the references; a redaction
    check proves no credential material rides along.

* Owed to the PM checklist
# one line per PM change, added to pm-change-checklist.org.
  - Build the three senders on the one bundle shape; add the no-secrets
    check to the gate.

** proot has no user namespaces, no ZFS, no real sandbox
# Anything needing isolation primitives must be stubbed behind a backend.
- What PM does: it states the rule and keeps such needs behind a backend, stubbed (X-5).
- The rule: design for the container that exists, not the one the manual describes.
- Verdict: REUSE.
- Read at: 0.FOUNDATION.org X-5.

** proot usually looks like root — neither require nor refuse it
# The only boundary is the configured prefix.
- What PM does: the tool does not require root and does not refuse root either; the rule is: never write outside the configured prefix (F-10).
- The rule: privilege is not the safety boundary here; the prefix is.
- Verdict: REUSE.
- Read at: 0.FOUNDATION.org F-10.

** Racket: the minimal plan grew into the full tarball

** Startup costs are measured and recorded
# Both languages pay a visible tax at every process start.
- What PM does: the Racket base startup baseline is 2.14s real; Nu's median is about 0.9s and cold runs reach several seconds; baselines live in one file and do not regress without a decision (X-1, X-2).
- The rule: on this phone, startup is a feature budget, and every measurement is written down.
- Verdict: REUSE.
- Read at: docs/PERF.org; docs/NU-NOTES.org.

** Nu: two versions coexist on the device
# A script never assumes which binary answers to its name.
- What PM does: the device carries a proot Nu and a Termux Nu at different versions; the pinned one lives under a versioned path and always runs with --no-config-file; a checker reports which binary would be used and fails clearly when none exists; nothing auto-downloads or self-updates.
- The rule: scripts name their interpreter or prove which one they found; they never inherit one.
- Verdict: REUSE.
- Read at: docs/NU-NOTES.org; docs/NU-ADOPTION.org; gate/need-nu.nu.

** Memory: the git GC envelope needed pinned threads
# Default parallelism exceeded what the phone tolerates.
- What PM does: git GC completes inside a 128MB virtual-address envelope only with a single pack thread and a bounded window memory; the default-threaded GC flaked on this phone, which is why the code pins the single thread.
- The rule: on this phone, parallelism in memory-hungry tools is a measured hazard, not a default.
- Verdict: REUSE.
- Read at: docs/PERF.org (vault-gc entry).

** Test cost: one shared process or five seconds a file
# The tiered workaround hid a real bug; the measurement removed the workaround.
- What PM does: running the test command per file costs about five seconds each on this phone; one shared process makes all later files cost milliseconds; an earlier fast/slow tier list turned out to be a workaround for an unspecified isolation problem, and a hang read as "that file is slow" instead of "that test leaks state".
- The rule: a slow file is an isolation bug to name and fix, never a tier to hide it in.
- Verdict: REUSE.
- Read at: docs/LESSONS.org (fast/slow tier entry); gate/test-runner.rkt.

** No timers anywhere
# Every wait ends on an event, never on a clock.
- What PM does: no timeouts, no polling, no sleeps, no heartbeats, no scheduled checks; every wait ends on a process exit, EOF, lock release or explicit cancel; a step that starts and never ends is the only thing that looks like a hang, so every step emits a start and an end record; the test runner reports slow files as information and nothing waits on them (D-015).
- The rule: a phone that polls is a phone that drains; make hangs visible instead of guessing timeouts.
- Verdict: REUSE.
- Read at: plan/DECISIONS.org D-015; gate/test-runner.rkt.

** The shared-process wedge: measured, blocked, honest
# One process for all tests is the target — and one spawn-heavy path still freezes.
- What PM does: three or more sequential vault-add calls inside one shared process froze with zero CPU and no live child processes (frozen 162s after one step); six single adds pass standalone; the suspects are the writer lock and a child-waiter family, and the fetch command stays blocked until a three-package fixture passes in one process; a queue-based workaround was rejected because it would hide the bug.
- The rule: the one-process design is a target, not yet a guarantee in spawn-heavy code — the new programs must re-run their own spawn-heavy suites before trusting it, and say so plainly when something is unproven.
- Verdict: ADAPT.
- Read at: plan/OPEN-DECISIONS.org (E-16b; the parked re-acquire test).

** Racket 9.3 cannot hold a fifo write end open
# A platform limit, probed and recorded instead of commented away.
- What PM does: all three file-open calls were probed against an existing fifo — two raise "file exists", the truncating and append variants return at once; no call blocks on a fifo write end, which is exactly what a holder needs; the belt-and-braces holder was written, measured not to work, and removed rather than shipped with a comment claiming a guarantee the code did not provide; the residual case is narrated through the wait door, and the one observed cause is guarded.
- The rule: never ship a comment promising what the platform cannot do; name the residual risk and make it visible.
- Verdict: REUSE — and a load-bearing fact for any terminal or pty work on this stack.
- Read at: plan/OPEN-DECISIONS.org ("the parent cannot hold a fifo writer open").

- What PM does: a large-blob vault test is parked because it needs about 100MB of synthetic fixture; a manual probe remains the proof instead.
- The rule: fixtures stay small and synthetic; a test that cannot run here is a manual proof with a name.
- Verdict: REUSE.
- Read at: plan/OPEN-DECISIONS.org (vault.rkt large-blob test — parked).

** Compiled output: one root, outside the tree
# The two-cache mistake is named so it cannot recur.
- What PM does: the gate sets a single compiled-output root outside the source tree; an earlier decision against redirecting was reversed after measuring that one root does not re-emit stock libraries (two roots would mean two caches, and two caches mean stale bytecode outliving its source); the old note stays where a reader who remembers the original decision will find it.
- The rule: bytecode caches are singular, out of the tree, and the reversal story is kept, not erased.
- Verdict: REUSE.
- Read at: gate/env.nu header; plan/OPEN-DECISIONS.org ("D-027 reversed").

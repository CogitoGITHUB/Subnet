#+TITLE: install-then-bake — a PM install feeds a program's dev bake
#+AUTHOR: Shape
# One job: let a program in dev mode bake against what PM installed,
# without the program knowing PM's store layout. Status: planned only;
# nothing here is built. Source:
# =../../pm-integration/install-then-bake.org= (the capability in
# words).

* Purpose
- The first thing a developer tries: install a package with PM, then
  bake the program that consumes it. Today dev mode cannot consume a PM
  install, so the two halves do not meet.
* Name and location
- name: the mechanism's parts are registered in step 3
- code: the producing side sits in the areas that own install state;
  the consuming side reads a stable sight file, not store internals
- area and layer: the home is the owner's open question (where the
  agent-side components live); either way the answer is a file read,
  not a new dependency
- may require: =install= and below, read-only
- may be required by: =entry=
* Public interface, in plain words
- after an install, a bake can ask where the installed package is and
  which generation is live; the answer is stable across generations.
* What it must never do
- Never leak store internals into the consumer: the sight file is the
  interface, the store is not.
- Never require a PM process to be running for a bake to work.
* Tests
- beside =install='s tests; one end-to-end fixture: install, then bake
  reads it.
* Docs it updates
- =plan/OPEN-DECISIONS.org= (the entry closes);
  =plan/NAMING-REGISTER.org=.
* Depends on new components
- =ai-sight-files= (where the consumer reads the state).
* Build order
- After the sight files; before =shell-environment= wants the same
  answer.

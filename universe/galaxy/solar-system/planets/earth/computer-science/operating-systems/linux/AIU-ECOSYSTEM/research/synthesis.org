* What transfers
# one line per mechanism worth carrying forward, grouped by program. No code.
  - Multiplexer (herdr, zellij): server/client split surviving detach;
    working/blocked/idle pane status; layouts as files; socket and CLI
    control for agents; keyboard and mouse both first-class; honest state
    after restore — processes do not survive, and neither do they on
    Android (tty-pty-proot-android).
  - Editor (helix, neovim-ui-model, neovim-ai-tools): modal selection
    model; core/UI split with attach and capability negotiation —
    least-capable client wins by default, the active set is announced;
    batched redraw events; widgets externalized only when asked; AI behind
    one ACP/MCP boundary; chat as a buffer; fast apply for token thrift.
  - Agents (opencode, hermes-agent, compared): both behind one boundary
    with pinned adapters; allow/ask/deny approvals with an explicit auto
    mode; skills as SKILL.md files discovered from project and home; rules
    via AGENTS.md; headless loopback server; from Hermes: skills improved
    by use, cross-session recall, backend as a choice, Termux-first
    packaging.
  - Notation (named-element-markups, org-outline-and-literate,
    incremental-parsing, language-server-design): one syntax with one
    parser description; literal, dispatchable names; context-free core,
    paragraph as default element; incremental reparse and error recovery
    as table stakes; content-addressed reuse (Babel's hash caching mirrors
    our journal); while editing, the session owns truth and files are
    storage.
  - Platform (key-input-and-escape, file-change-events): adopt the kitty
    keyboard protocol's opt-in flags rather than inventing key encoding;
    watch files with inotify events, never polling; accept that processes
    die and resume from disk.

* What to avoid
# one line per mechanism left out, grouped.
  - Plugin runtimes (zellij WebAssembly, opencode plugins): extension
    surfaces stay MCP and skills.
  - Surfaces this phone does not need: desktop apps, web clients,
    multiplayer collaboration, messaging gateways.
  - Matrices: many LLM providers, six chat platforms, seven execution
    backends, RAG inside the editor — one path first, adapters later.
  - Fragile floors: timing heuristics for input, polling for file
    changes, assuming background processes survive Android.

* Options for the Rust projects
# options for the multiplexer and the editor side, with a recommendation. This is the research-level view, not a decision.
  - Option A — adopt: run herdr (multiplexer) and/or helix or neovim
    (editor) as-is and write our rules around them. Fastest to usable;
    binds our rules to someone else's roadmap; plugin marketplaces and
    Lua layers are weight we would not choose.
  - Option B — build our own small Rust programs, borrowing the
    architectures above: one binary per job, names and contracts ours,
    phone budget ours. Best fit for the ecosystem laws; slowest.
  - Option C — hybrid: adopt an existing multiplexer for now while the
    editor and notation core are built as our own Rust programs, with the
    multiplexer migrated later behind the same contract.
  - Recommendation: C, with B as the destination and A as the fallback if
    this phone cannot build Rust at usable speed. The test below decides.

* What this phone can build
# what the constraints allow, honestly; unverified until the test below runs.
  - Small single-purpose Rust binaries; no Electron, no Chromium, no local
    embedding servers (memory, battery, proot).
  - Foreground-first tools with on-disk session state; few long-lived
    processes (phantom killer, see tty-pty-proot-android).
  - Evidence the target is real: Hermes ships an aarch64 Termux package;
    Termux maintains proot and proot-distro. Our own build times remain
    unmeasured.
  - First testable milestone: build one tiny Rust binary on this phone,
    inside proot, with the UI-attach or socket seam, and measure — before
    any commitment.

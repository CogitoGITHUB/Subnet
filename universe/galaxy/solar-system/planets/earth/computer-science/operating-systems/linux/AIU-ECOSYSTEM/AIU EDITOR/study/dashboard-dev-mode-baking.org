#+TITLE: Dashboard: dev-mode baking
# One job: what baking means for the dashboard: what is baked, what stays live, what survives
# Status: filled 2026-10-16 from Cyberdeck-Emacs, read-only; not yet reviewed.

* What baking means here
# what of the dashboard is baked into the binary as a first-class default.
  - Today the desk loads as ordered units — vendored engine first, then the
    declarations, setup composing, install last — and renders at startup when
    no file was passed.
  - Baking compiles the declarations into the binary as defaults: the widget
    registry, the composed order, the segment rows, the banner words, the
    faces and the refresh policy.
  - A baked binary opens straight to the desk, loads no config, and prints
    its measured start time.

* What stays live in work mode
# what is still loaded from source while working.
  - Editing a widget file, the order file, a segment or the banner words and
    reloading changes the desk; saving the order file already re-applies it
    live today.
  - The validator and scaffolder run on reload: new widget skeletons are
    picked up, orphans are reported.
  - The order file stays outside compiled discovery on purpose — a data file
    that is read and written at runtime.
  - Temporary tuning (a face, a length) is expected to be live-only until the
    next bake.

* What survives a rebuild
# the guarantees this layer keeps across a bake.
  - The declarations are the single source: both modes produce the same
    sections, order and bar; a bake changes open time, not content.
  - Failure degrades instead of breaking: a bad bar shows the plain bar, a
    sick segment shows "?"; the baked desk must keep that property.
  - The vendored-engine discipline does not survive — a rebuild re-owns the
    engine — but the contracts it was kept behind (widget, segment, order)
    do.
  - Open questions carried to the plan: what a clean validator report means
    for a bake, and what replaces the stage tags in the new format.

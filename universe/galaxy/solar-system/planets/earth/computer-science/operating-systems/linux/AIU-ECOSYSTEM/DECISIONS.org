** 2026-10-21 D-019: the Git integration — one read-only layer, Rust, read-only by construction
   Touches AIU-ECOSYSTEM/shared-layers/git-inspection/INDEX.org; AIU-ECOSYSTEM/shared-layers/git-inspection/plan/git-inspection.org; AIU-ECOSYSTEM/shared-layers/git-inspection/Cargo.toml; AIU-ECOSYSTEM/shared-layers/git-inspection/src/; AIU-ECOSYSTEM/INDEX.org.
1. WHAT: the Git integration is one layer of its own at =AIU-ECOSYSTEM/shared-layers/git-inspection/=, written in Rust, used in-process by the multiplexer and over the editor's join seam (D-008) by the editor. It owns the discovery, the commands, the parsing, the states and the freshness; both programs read the same model, so there is one Git parser and one meaning. It is read-only by construction: the command is a typed choice with no variant for anything that writes, every command runs with a structured argument list in an explicit working directory, no shell is ever involved, and no command reaches a remote. The states stay apart: the working tree, the index, the editor's buffer, and the branch's distance from its upstream are four different fields, and the counts of ahead and behind come from the refs that are here, so a missing upstream is UNKNOWN and never "up to date". The worktrees are first-class and share the repository's objects. A change of state is a different program with declared permissions, not a call into this one.
2. WHY: the owner asked for one shared, strictly read-only Git foundation across the editor and the multiplexer, with the file changes and the unpushed commits never conflated, and with the architecture left modular for a later workflow layer that may act through explicit permissions. Rust keeps the layer inside the multiplexer, which is frozen to two crates, and meets the editor at the seam that already carries the two languages.

** 2026-10-21 D-018: the shared workspace — one engine above both programs, files for a store, no daemon
   Touches AIU-ECOSYSTEM/WORKSPACE.org; AIU-ECOSYSTEM/contract/workspace-model.org; AIU-ECOSYSTEM/contract/workspace-operations.org; AIU-ECOSYSTEM/contract/workspace-mode-line.org; AIU-ECOSYSTEM/contract/workspace-ai-context.org; AIU-ECOSYSTEM/contract/INDEX.org; AIU-ECOSYSTEM/INDEX.org.
1. WHAT: the workspace becomes a system object above the editor and the multiplexer. It holds workspaces, projects, resource references, presentations and the shared context; it holds no buffer text, no pty and no process. The editor keeps its buffers, tabs and modes; the multiplexer keeps its tabs, panes and sessions; neither writes the other's part, and closing one leaves the other and the workspace untouched. The engine is one Rust package of its own at =AIU-ECOSYSTEM/shared-layers/workspace/=, used in-process by the multiplexer and through the editor's join seam (D-008) by the editor. The store is files in one state directory that is an argument, written by write-beside-and-rename under a one-writer lock, read without a lock. Operations travel in one envelope over two channels: the engine for workspace state, the holder's own socket for the multiplexer's resources, and the editor's mailbox in the engine for the editor's resources. The mode lines of both programs show the same workspace and project facts, and the agent reads a versioned snapshot instead of the screen.
2. WHY: the owner asked for a workspace that both programs read and control without either owning the other's state, and for an architecture that does not become a daemon, a database or a new dependency. The audit found that the holder's socket, the editor's join seam and the editor's lock already prove the shapes this needs, so the engine adds no new mechanism; it gives the two programs one model, one set of words and one place where the truth lives.

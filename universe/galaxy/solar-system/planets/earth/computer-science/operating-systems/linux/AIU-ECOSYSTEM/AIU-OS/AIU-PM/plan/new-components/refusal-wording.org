* Purpose
- The confirmation refusal always appends "pass it as the
  confirmationToken argument", even when the token was already used or
  belongs to another plan. A refusal with the wrong next step teaches
  the wrong habit in the reader: the agent retries the wrong way.
- Each refusal gets its own next step: use the token once; ask for a
  fresh one; re-read the plan the token names.
* Name and location
- name: none new; the refusal texts change, keyed by refusal reason
- code: =src/entry/mcp-tools.rkt= (the refusal path), and the CLI's
  copy of the same refusal if it exists
- area and layer: =entry= (area 13)
- may require: as it already does
- may be required by: nothing
* Public interface, in plain words
- unchanged shape: a refusal still names why and what next; only the
  "what next" becomes true per case.
* What it must never do
- Never one sentence for every case: a refusal that lies is worse than
  a bare no.
* Tests
- =tests/security/confirmation-test.rkt= section 7: one test per refusal
  reason; the already-used and wrong-plan cases assert their own next
  step.
* Docs it updates
- none: the entry README has no refusal section (checked 2026-10-18).
* Depends on new components
- none.
* Build order
- Any time; small; after the MCP additions if both touch the same
  file, so the texts move once.

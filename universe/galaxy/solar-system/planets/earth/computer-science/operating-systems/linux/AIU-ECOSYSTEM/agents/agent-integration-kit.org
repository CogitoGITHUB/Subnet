#+TITLE: Agent integration kit
# One job: the standard kit every package ships and the template its own checklist follows
# Status: filled 2026-10-16; recommendations await owner review.

* The questions
# the questions this file must answer, listed before any option is weighed.
  - What is in the kit, exactly, and what is derived rather than written
    by hand?
  - Is the kit a shared runtime or a shape each program implements itself?
  - How does a program's checklist prove its kit conforms, cheaply and
    mechanically?

* Options
# two or three real options, each with what it costs and what it gives.
  - Option A — a shared kit library every program links. Cost: a common
    runtime across the four programs — the temptation the learned notes
    refuse: the four programs share a contract, not a runtime. Gain: one
    place to fix one bug.
  - Option B — a specification plus template plus conformance checklist;
    each program implements the four surfaces itself. Cost: four small
    implementations and four gates instead of one. Gain: crash isolation,
    no coupling, and each program's kit auditable in its own tree.
  - Option C — generate the kit from the program's capability table at
    build time. Cost: generation hides the surfaces from readers; one
    table shape becomes everyone's. Gain: drift between table and surface
    becomes impossible.

* Recommendation
# one recommendation, named plainly, with its reason.
  B, keeping C's one good idea: the kit is a written shape, derived from
  the program's declared capability table, and a gate fails when
  declaration and surfaces disagree. The kit itself is the four surfaces
  the rules already demand — the engine, an MCP server over it, a skill
  whose examples run in the suite, a read-only plugin — plus the event
  feed and the sight files an agent reads without asking. Read is free;
  mutation needs the human token, and the engine re-checks it. Nothing in
  the kit may hold logic the engine lacks.

* The checklist every kit must satisfy
# the template its own checklist follows: one line per proof the gate runs.
  - One object per line, one envelope, fixed key order, every operand a
    string.
  - Refusals exit 0 and name their rule; errors are exit codes, never
    error objects.
  - Every mutating MCP tool refuses without the human token; the engine
    re-checks the confirmation itself.
  - Every skill example executes in the test suite; a stale example fails
    the build.
  - The plugin is read-only, file-watcher driven, never polling, never a
    mutating tool.
  - The feed flushes per record; a WAIT precedes any block; a WAIT with
    no WAIT-DONE names the hang.

* What it needs from the package manager
# anything this design needs from PM, marked for the later PM prompt.
  - PM ships its own kit entry declaring its capabilities (step 7,
    kit-entry.org) and stands as the first worked example of the template.
  - PM's change checklist (pm-change-checklist.org) runs this checklist's
    items for PM later.

* Open decisions
# what remains undecided and who decides it.
  - The checklist's final item list: frozen with the contract (step 9,
    kit-format.org) — owner reviews there.
  - The skill's prose budget around its executable examples — owner at the
    freeze.

#+TITLE: Node addressing and comments
# One job: how a send names its notation address and how comments in the text are treated
# Status: filled 2026-10-16; working draft until a program and an adapter both depend on it.

* What this freezes
# the exact thing every program and adapter must obey; if it is not frozen here, authors guess.
  The notation address a bundle carries, and the treatment of comments:
  first-class in the text, stripped by rendering, stripped by nothing
  else (the notation's design; the bundle's neighbour file).

* Shape
# names and meanings only: the fields and what they promise. No code, no examples.
  - Address: names a node by kind and position — title, paragraph, code
    block, chunk — computed, never authored; stable while the document
    is edited elsewhere; readable by the owner and by an agent alike.
  - Comments: parse keeps them; rendering strips them; a send carries
    the text as it is, comments included — they are meaning, not noise.
  - One vocabulary across programs: the editor, the multiplexer and PM's
    senders all use the same address shape in bundles.

* Who obeys it
# every program and adapter this applies to, named.
  The notation computes addresses; the editor and the multiplexer place
  them in bundles; agents read them. PM's senders use file paths where
  no notation exists — an address is never invented.

* How it changes
# how this can change without breaking a running client; point at a D-number once one exists.
  The address shape is additive if it must grow; readers treat what they
  do not know as opaque text. Freeze condition: a program and an adapter
  both depend on it; none yet.

* Open decisions
# options with a recommendation, or none yet.
  - The address spelling — recommendation: literal names plus computed
    numbers, matching the auto-numbered headings the owner asked about.
  - Whether rendering may show comments on request — recommendation:
    yes, by an explicit request only, never by default.

#+TITLE: The open and close mark
# One job: how a named element is opened and closed, and what may sit inside it
# Status: decided 2026-10-17 by the owner and revised the same day (notation D-014); the parser side starts at TODO item 2.

* What it is for
# why this exists: so a name can be opened and closed in words, with nothing new to remember per element.
  - Ordinary things are written as names, not as symbols: a title is called
    title, a paragraph is called paragraph, a code block is called code block.

* The opening and closing lines
# the shape, in words; no code here, the implementation is TODO item 2.
  - No braces and no enclosing mark. A block is opened by a line that reads
    "<name> start" and closed by a line that reads "<name> end", each alone on
    its own line, and the name in the closing line is the same name that
    opened it.
  - The block's text sits between those two lines. Nothing marks the start or
    the end except the word itself.

* Everything lives inside a block
# the law: a notation file is a stack of named blocks, nothing else.
  - Every element is a block, paragraphs included. There is no default
    paragraph and no plain line that means anything on its own.
  - Blank lines and whitespace between blocks carry no meaning.
  - Text outside any block is an error named "stray text": severity error, no
    off switch. The text is kept exactly as written, never deleted and never
    rewritten, and the rest of the file keeps parsing.
  - The meaning tree has no node kind for loose text: it holds blocks and
    error nodes, nothing else.
  - The engine enforces this; the editor only shows what the engine reports,
    through the boundary.

* Nesting
# blocks may sit inside blocks, so the parser keeps a stack.
  - Blocks nest: a comment block may sit inside a title block.
  - A closing line must match the block that is innermost and still open. If it
    does not, that is a precise error naming the line where the open block
    started, and the text stays untouched.

* Opaque bodies
# what the parser refuses to read inside.
  - A code block's body is opaque: the parser does not read it as notation, so
    only an exact matching "<name> end" line closes it. A word that matches,
    but sits inside a line of text or a line of code, closes nothing.

* Styling is a hint, never meaning
# declared inside the block, under its start line.
  - Styling is written on keyword-colon lines straight under the start line:
    style, theme, color, format, font and so on.
  - Those lines are stored as hints. They never change what an element means.
  - A terminal honors bold, italic and color and ignores the rest.

* Reuse by an authored id — Tier 2, design note only
# not decided, no files; recorded so the shape is known before it is built.
  - A block may later be included in another file by reference. That needs an
    optional authored id line inside the block, distinct from its title and
    from its path.
  - Includes are followed by the reference resolver, never by the parser, and
    an include cycle is an error.
  - This is Tier 2. No file is created for it until the owner opens Tier 2, and
    the contract question in ROOT-REQUEST-D014.org is answered first: the
    contract says addresses are computed and never authored, while an authored
    id is a different thing and must not collide with it.

* Still open
# questions the owner has not answered; nothing here decides them.
  - Inline emphasis and links inside a paragraph: open, not decided.
  - The Tier 2 element list (comment, citation, tables and so on): open.

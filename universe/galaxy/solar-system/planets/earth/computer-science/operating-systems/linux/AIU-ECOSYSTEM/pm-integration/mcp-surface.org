#+TITLE: MCP surface
# One job: PM's MCP surface: search, install, status, build, bake
# Status: filled 2026-10-16; planned only, PM itself is not touched here.

* What PM must gain
# the capability in words; the exact PM files are named only after PM is read, until then say where to look later.
  - The five named operations exposed as MCP tools with the split that
    already rules PM: search and status read — free; install, build and
    bake mutate — each requires the human token, re-checked by the engine
    itself.
  - The same envelope the CLI prints: same key order, one object per
    line; the MCP surface stays a reader and never a second
    implementation of any decision.
  - Refusals from MCP name their rule; asking "what would this do?"
    returns the full plan and changes nothing.

* Shape
# how the entry, surface or file looks from the outside. No code.
  - search — find packages by name and slot among the specs PM knows.
  - status — what is installed, which generation is current, where the
    state directory lives; reads the sight files.
  - install — resolve, fetch, build, place, flip the generation; without
    the token it prints the full plan and changes nothing.
  - build — build from a spec or a dev checkout without activating.
  - bake — ask the installed program's dev-mode loop for its artifact
    (install-then-bake.org); explicit, never a side effect of install.
  - Tools carry command names, never surface-only verbs.

* Proof that it works
# the one check that shows this is done when the PM prompt runs.
  - A test that every mutating tool refuses without the token and that
    the engine re-checks the confirmation — approval at the surface is
    never authorization in the engine; documented examples run in the
    suite.

* Owed to the PM checklist
# one line per PM change, added to pm-change-checklist.org.
  - Cover search, install, status, build and bake with MCP tools and
    gating tests; add bake as an explicit verb with its own case.

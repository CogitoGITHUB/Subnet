#+TITLE: Dashboard mechanisms
# One job: every mechanism the dashboard combines, one line each
# Status: filled 2026-10-16 from Cyberdeck-Emacs, read-only; not yet reviewed.

* The mechanisms
# every mechanism the dashboard combines, one line each, described plainly.
  - Vendored engine — the upstream dashboard (mode, navigation, item
    insertion) carried whole inside the desk; local config lives outside
    those blocks.
  - Vendored stock widgets — recents, bookmarks, projects, agenda, registers,
    plus directory and file listings; upstream behavior kept whole.
  - Section machinery — the item list becomes sections; separators are
    inserted between them; section starts are remembered; number keys jump.
  - Startupify list — the fixed render sequence: banner, title, navigator,
    items, footer.
  - Navigation — section next/previous with optional cycling, item-aware line
    movement, return/click activation.
  - Item removal — backspace/delete removes the item under point from its
    source (recentf, bookmarks, projects, agenda).
  - Banner engine — the box is drawn for the available width in three tiers
    (full title, wrapped compact title, inner box only); the words are data.
  - Banner resize — debounced idle re-render that erases and redraws; the
    upstream stacking resize hook is removed, twice if it comes back.
  - Widget DSL — one declaration per widget writes the generator, the item
    entry and the registry push; deleting the file unregisters it next boot.
  - Widget registry — key and display length per widget, in load order; the
    length sits beside the code that renders the section.
  - Widget scaffolder — a command writes a new widget file from the skeleton;
    loud when the file exists; one wanted-list line in setup.
  - Widget validator — every registered widget has a generator, a sane length
    and a real file; every widget file is claimed by a widget; order keys
    resolve; the orphan check exists because five dead files once passed the
    old check.
  - Order file — one data file lists section keys top to bottom; boot
    composes the item list from it, appends new widgets, prunes dead ones,
    never reorders and never touches stock entries.
  - Order audit — keys matching nothing are reported, never deleted.
  - Order live loop — saving the order file re-applies it and refreshes a
    visible dashboard.
  - Stock items — upstream sections and their lengths, listed in the order
    file, never pruned.
  - Desk faces — mono white tuning for banner, headings, items and footer;
    re-applied after theme load and on new frames.
  - Desk mode hook — the dashboard buffer runs with no model line, centered
    by olivetti, and with its own jump keys.
  - Bounded agenda — the stock agenda widget is off: it used to walk every
    org file at boot; the real agenda is one key away.
  - Recentf wiring — recent files stay on, saved periodically, and a save
    refreshes a visible dashboard at most every two minutes.
  - Startup policy — the dashboard appears only when the editor was started
    with no files; resize stacking is fixed at the source.
  - Status widget — boot time with a sparkline, errors and warnings, vault
    note counts, git state; rewritten in place every thirty seconds.
  - Small registry widgets — todos collected from the modules, a random
    Sartre quote; both are ordinary registry widgets.
  - Modeline segment DSL — one registry of zero-argument render functions;
    rendering never throws (a sick segment shows "?") and never adds lines.
  - Modeline order file — the bar's layout as data: two rows, left and right,
    segment keys under each; row 1 identity, row 2 context.
  - Modeline composer — reads the order, renders each side as exactly two
    lines, and leaves a single-row fallback for the real mode line.
  - Modeline install — its own unit, last slot: the one call that starts the
    bar; it exists because everything else was green and the bar never
    appeared.
  - Modeline segments — keyboard state, modified letter, buffer name,
    line/column/percent, branch, cyberdeck letters, doctor string, datetime
    with fuzzy words.
  - Modeline refresh — state changes push the bar; cyberdeck letters cache on
    a minute timer; the doctor string is called directly, never twice.
  - Mini-modeline — the bar lives in the minibuffer as two stacked rows; the
    real mode line is hidden; the dashboard buffer shows none at all.
  - Messages shim — a copy of each message goes to *Messages* before the
    minibuffer display reroutes it.
  - Fuzzy clock — vendored words-for-time library; ships inline, its own mode
    stays off, the datetime segment reads it directly.
  - Migrated manual text — the mode-line reference travels inside the units
    it documents, so the reference ships with the code.

* How they combine
# the order input passes through them.
  - At load, the desk lane runs: vendored widgets, vendored engine, the
    widget DSL, widgets, banner, faces, then setup — which composes the item
    list from the order file and installs hooks.
  - The bar is its own lane near the same priority: package config, stock
    reference, segment DSL, composer, faces, segments, and install as the
    last call.
  - At open: banner for the width, title, items in order-file order (each
    from its widget), footer; separators are inserted after the pieces are
    in place.
  - While running: a save refreshes recentf and throttles a full redraw; the
    status widget rewrites only its lines on its own timer; a resize
    debounces into a full erase-and-redraw; the bar pushes on state changes.
  - The desk and the bar are separate surfaces: the desk owns the buffer, the
    bar owns the minibuffer row, and both read the same keyboard state (the
    state segment keeps no copy).

* What is portable
# which mechanisms are not specific to the old config and can travel.
  - The vendored engine split from local declarations: the engine can be
    replaced without touching the declarations.
  - The widget contract: name, length, render body; registration is dropping
    a tagged file, deregistration is deleting it.
  - Order as data: a user-editable order file over a code-owned registry,
    with reconcile and audit rules.
  - Validation discipline: registry against reality, including the orphan
    direction.
  - Bar model: segments as pure single-line renderers, rows and sides as
    data, the two-line pairing invariant.
  - Refresh discipline: cache the slow values, push on events, rewrite in
    place when one section changes, throttle full redraws.
  - Startup policy: render only when there is nothing else to show; degrade
    to the plain bar instead of a broken one.

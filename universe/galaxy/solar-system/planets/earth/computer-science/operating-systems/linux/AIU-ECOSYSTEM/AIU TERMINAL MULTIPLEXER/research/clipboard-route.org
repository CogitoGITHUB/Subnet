#+TITLE: The clipboard route on this phone — what really reaches the Android clipboard
# One job: the measured facts about the two routes the owner named, so the
# clipboard bridge is built on the route that works and not on the one that
# only looks like it works.
# Status: current; measured on 2026-10-22 on this phone, inside the proot.

* The question
# what the owner asked, in their words.
The owner asked (TODO item 24) which routes really reach the Android clipboard
from inside the proot and the multiplexer: the terminal's own clipboard escape
sequence, and the Termux clipboard tools. Each route is measured here, with the
real output. The build follows this file, not the other way round.

* The phone
# what is installed, measured, not assumed.
  - The Termux app is =com.termux=, versionCode 1020 (that is v0.119.0-beta.1
    or v0.118.x; the F-Droid index maps 0.118.3 to 1002 and 0.119.0-beta.2 to
    1021, so 1020 sits just under the 0.119 betas).
  - The Termux:API add-on is NOT installed: =pm list packages= names only
    =com.termux= and =com.termux.x11=. This is the whole reason for the
    finding below.
  - Termux:X11 is installed (versionCode 15) but its server is not running and
    the X11 clipboard tools (=xclip=, =xsel=) are not installed.

* Route one: the terminal's own escape sequence (OSC 52) — WORKS
# the sequence is ESC ] 52 ; c ; <base64> BEL.
Termux's terminal emulator has handled OSC 52 since its first commit (2015),
with no setting to turn on. The payload is base64-decoded and handed to
=ClipboardManager.setPrimaryClip=, so it lands in the ANDROID system clipboard,
not only in the terminal's own buffer. Proof that the code is in THIS app: the
installed APK's dex carries =onCopyTextToClipboard= and =copyTextToClipboard=
(class strings), and no OSC-52 strings of its own — the sequence is handled by
the emulator, not by a script.

Two limits, both from the emulator's own code:
  - The payload is capped: =MAX_OSC_STRING_LENGTH = 8192= characters in the
    released versions (v0.118.0 and the 0.119 betas). A longer copy is dropped
    silently. The master branch raised the cap to about 100 KB, but that is
    unreleased, so this phone still has 8192.
  - The write only happens while the Termux terminal activity is VISIBLE. The
    session-backed client has an EMPTY =onCopyTextToClipboard=, so a copy
    made while Termux is in the background goes nowhere.

Reading the clipboard back with OSC 52 does NOT work: the emulator has no
answer to the =? = query (Termux issue 2373; the maintainer's own words: "OSC
52 is already supported for setting clipboard, but copying clipboard is not
supported"). So OSC 52 is one direction only: out of the terminal.

For the multiplexer this means: the OSC 52 bytes must be written by the
multiplexer to the client's OWN stdout, exactly as Zellij does it
(=SendVteInstructionToClients= in zellij-server/src/tab/clipboard.rs). The
multiplexer's screen redraws the pane text and does NOT pass a pane's raw
escape sequences through to the terminal, so a pane that prints OSC 52 itself
reaches nothing. The multiplexer must emit the sequence itself.

* Route two: the Termux clipboard tools — FAILS
# the tools are there; the app they need is not.
The tools are installed and runnable:
  - =/data/data/com.termux/files/usr/bin/termux-clipboard-set= and
    =-get= exist and are executable.
  - But they are only shims: each one runs
    =/data/data/com.termux/files/usr/libexec/termux-api Clipboard ...=, and
    that helper is =termux-api-broadcast=, a native binary that sends an
    intent to =com.termux.api/.TermuxApiReceiver= and WAITS on a socketpair
    for the add-on's answer.
  - The add-on is not installed, so nobody answers, so the tool waits for
    ever. Measured: =timeout 15 termux-clipboard-set "aiu-clipboard-route-test"=
    exits 124 with no output at all, and =termux-clipboard-get= exits 124 the
    same way.
  - The wait is not in =am=: =am --version= answers 0.8.0 inside the proot, and
    a direct =am broadcast -a com.termux.api/.TermuxApiReceiver ...= answers
    "Broadcast sent without waiting for result" and exits 0. The broadcast
    goes out; the answer never comes, because the add-on that would answer it
    is not on the phone.

So this route is dead on this phone, and it hangs rather than fails: any code
that calls it MUST be given a bound, or the call never returns.

* What was ruled out, and how
# the other ways that looked possible.
  - =cmd clipboard= — not implemented on this Android build (=cmd clipboard=
    exits 255). It is not a route.
  - The Android clipboard service through =service call clipboard= — the
    transaction numbers drift between Android versions and it is not a
    documented interface. Not a route to build on.
  - Termux:X11's clipboard sharing — it does sync the X11 selection with the
    Android clipboard (the pref =clipboardEnable= is on by default), but the
    X11 server is not running and =xclip=/=xsel= are not installed here. It
    stays a later plan.

* The route the bridge is built on
# the decision, and the one direction that needs an answer.
  - COPY OUT (the multiplexer's ring or a picked region to the Android
    clipboard): OSC 52, written by the multiplexer to the client's stdout.
    The base64 must be chunked so that no single OSC string passes the 8192
    cap — and the chunks are what the emulator's cap applies to, so the
    bridge must split the text before it encodes it, not after.
  - PASTE IN (the Android clipboard into a focused pane): OSC 52 cannot read
    back. The only route on this phone is the Termux:API add-on, which is not
    installed. Until the owner installs it, the bridge must SAY SO BY NAME
    ("the Termux:API add-on is not installed") instead of hanging or doing
    nothing — that is what item 24 asks for.

* The sources
# where each fact came from.
  - Termux's own source: =termux-app/src/main/java/com/termux/terminal/TerminalEmulator.java=
    (the =case 52= of the OSC handler), and
    =app/src/main/java/com/termux/app/terminal/TermuxTerminalSessionActivityClient.java=
    (the =onCopyTextToClipboard= that calls =ClipboardManager.setPrimaryClip=).
  - Termux issue 2373 — "OSC 52 clipboard pasting not work": the read side is
    not supported.
  - The F-Droid index for =com.termux= — the versionCode to version mapping.
  - Zellij's own way of doing it: =zellij-server/src/tab/clipboard.rs= and
    =zellij-server/src/tab/mod.rs= (=write_selection_to_clipboard= sends the
    OSC 52 to every connected client, never to the host's own clipboard).

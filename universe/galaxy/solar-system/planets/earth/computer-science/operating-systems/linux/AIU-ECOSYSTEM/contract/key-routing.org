#+TITLE: Key routing
# One job: how a key finds its owner across multiplexer, editor and the programs inside panes
# Status: filled 2026-10-16; working draft until a program and an adapter both depend on it.

* What this freezes
# the exact thing every program and adapter must obey; if it is not frozen here, authors guess.
  First-receiver routing and the reserved prefix: a key reaches the
  focused pane's program before any layer above; the multiplexer keeps a
  reserved prefix for its own actions; the keyboard layer owns the
  routes (rules 07 and 13; the studies).

* Shape
# names and meanings only: the fields and what they promise. No code, no examples.
  - Order: pane program first; then the editor's inner layers; the
    multiplexer's reserved prefix applies everywhere.
  - Selection and send keys exist wherever something selectable exists —
    buffer, pane, command record, status line.
  - Routes are data: named, listable, testable; the kit's command table
    covers them.
  - Disambiguation uses the terminal's keyboard protocol (the kitty
    flags), never our own chord timers.
  - No mouse required anywhere; the mouse may work.

* Who obeys it
# every program and adapter this applies to, named.
  The multiplexer (first receiver, reserved prefix); the editor (inner
  routing); every program in a pane, agent panes included.

* How it changes
# how this can change without breaking a running client; point at a D-number once one exists.
  Routes are additive; a route that collides with the reserved prefix is
  refused by a gate. Freeze condition: a program and an adapter both
  depend on it; none yet.

* Open decisions
# options with a recommendation, or none yet.
  - The reserved prefix — recommendation: one named prefix, declared in
    the layout, collisions refused; the exact key is the editor's open
    decision resolved alongside this one.
  - Handover documentation — recommendation: one routing table in the
    multiplexer's docs, generated from the routes, tested by the walk.

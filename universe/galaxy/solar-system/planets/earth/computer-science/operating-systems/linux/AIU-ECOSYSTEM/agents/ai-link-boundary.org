#+TITLE: AI-link boundary design
# One job: the design of the agent-neutral boundary, options with a recommendation
# Status: filled 2026-10-16; recommendations await owner review.

* The questions
# the questions this file must answer, listed before any option is weighed.
  - What does a program call when it hands work to an agent, in terms that
    survive either agent changing its own interface?
  - Where does the boundary sit: in each program, in a shared package, or
    in the multiplexer's session holder?
  - What crosses it — a send carries a context bundle (selection, file,
    position, notation address, why); the agent side carries events,
    permission asks and cancellations — and which direction may mutate?
  - When one adapter is pinned first and the second follows behind the same
    contract, does the boundary hold both without doubling?

* Options
# two or three real options, each with what it costs and what it gives.
  - Option A — one small internal contract: a JSON-lines boundary owned
    here, one object per line, fixed key order, with one thin pinned
    adapter per agent translating to that agent natively. Cost: we keep
    the mapping, and every agent change lands in its adapter. Gain: total
    control; the house envelope law holds across the whole link; no
    unverified protocol carries a promise we make.
  - Option B — ACP as the boundary, adapters as ACP clients. Cost: ACP is
    verified only for OpenCode; for Hermes nothing read mentions it, and
    the compared study says the boundary design may hinge on this; it is
    also another project's versioning to track. Gain: a standard shape,
    already proven in editor plugins; less bespoke surface to defend.
  - Option C — no protocol: programs address agent panes as screens and
    pass text through the session holder. Cost: no structured events, no
    permission channel, nothing to checkpoint or narrate honestly. Gain:
    the smallest seam to build today; kept here only to name the cost we
    refuse.

* Recommendation
# one recommendation, named plainly, with its reason.
  A — the AI link is one small contract owned here: one object per line,
  fixed key order, read and mutate told apart from the first version.
  Reason: the boundary must not wait on an unread docs page or another
  project's release rhythm, and Hermes' protocol posture is unverified
  today. Where an agent speaks ACP, its adapter may prefer ACP as the
  wire underneath — so ACP adoption stays possible without becoming the
  hinge. The contract freezes this shape in step 9
  (contract/ai-link-boundary.org, agent-adapters.org).

* What it needs from the package manager
# anything this design needs from PM, marked for the later PM prompt.
  - Adapters packaged as versioned, pinned packages: generations, atomic
    flip, rollback — the PM pattern in learned/versioning-and-rollback.org,
    with its own step-7 file (adapter-versioning-and-rollback.org).
  - Each adapter names the boundary version it implements; a program built
    against a new boundary refuses a stale adapter instead of guessing.
  - PM's own sends to agents use this same boundary (step 7,
    context-bundle-senders.org).

* Open decisions
# what remains undecided and who decides it.
  - ACP as the wire under an adapter: confirm after the ACP pages are read
    (OpenCode's is unread; Hermes' existence unverified) — contract step 9,
    owner reads it there.
  - Which adapter is pinned first: after the proot test — owner.

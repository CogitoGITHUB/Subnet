#+TITLE: Workspace operations
# One job: the one operation envelope, the operations themselves, and the
# rules that say who may ask for what.
# Status: written 2026-10-21 from the owner's unified workspace specification;
# the working draft until a program and an adapter both depend on it.

* The envelope
# every operation, in every direction, in one shape.
  An operation is one JSON object with these fields, and no others:
  - protocol — the version of this envelope, "workspace-operations/1".
  - request — an identifier that names this one request.
  - op — the name of the operation.
  - target — the resource the operation is about, by its stable identity.
  - workspace — the workspace the operation belongs to.
  - project — the project the operation belongs to, if any.
  - args — the arguments, checked against the operation's own shape.
  - origin — the program that asked: "editor" or "multiplexer".
  - auth — what the requester claims to be allowed to do. A claim is never
    the permission: the program that owns the target checks it.
  - expect — the version the requester believes it is acting on, when the
    operation depends on one.

* The states of an operation
# what "done" means, and what it does not.
  - accepted — the operation was taken and is understood.
  - running — the owner is carrying it out.
  - completed — it was carried out and the result is recorded.
  - rejected — the owner refused it, and the refusal names the rule.
  - failed — it was understood and could not be done.
  - unavailable — the owner that would do it is not running.
  - Delivery is not completion. An accepted operation says nothing about
    whether it was done; only completed says that.
  - A duplicate request with the same request identifier is answered with
    the state of the first one, and never run twice. That is what keeps a
    retried destructive request from happening twice.

* The operations
# the catalogue, split by what they touch.
  - Reading the workspace: list workspaces, read one workspace, list its
    projects, read one project, read the active context, list the
    presentations, read one presentation.
  - Reading resources: list the resources of a project, list them by kind,
    list them by owner, list the ones that are live, list the ones that
    carry a tag, list the ones that point at a document or a workflow.
  - Writing the workspace: create a workspace, rename one, select one,
    register a project, rename a project, remove a project, register a
    resource reference, update one, unregister one, create a presentation,
    rename one, delete one, read and write the shared context, validate
    the whole workspace.
  - From the editor to the multiplexer: list the terminal tabs, focus a
    tab, focus a pane, open a terminal for the active project, run a
    command in a named terminal, read the output of a terminal.
  - From the multiplexer to the editor: open a file, focus an editor
    buffer, open a new editor tab, focus the editor's active context.

* Who may ask for what
# the permission boundary, checked by the owner of the target.
  - A read of the workspace is free. It changes nothing, so it needs no
    human.
  - A write to the workspace metadata is free for the owner of the
    workspace: the two programs may both register and unregister.
  - An operation that touches another program's resources is allowed by
    that program's own rules, and only that program's rules. The requester
    never decides.
  - An operation that runs a process, closes a tab, stops a terminal or
    changes what is on the screen asks the human first. The request says
    what it wants; the owner of the resource asks.
  - A file path that comes from workspace metadata is data, never a
    command. Nothing in a project file may make a program run anything.

* The two channels
# how an operation reaches the program that owns the target.
  - Workspace operations go to the workspace engine. The engine is one
    program with one implementation; the editor reaches it through the
    join seam that already carries the two languages, and the multiplexer
    reaches it in its own process. The engine answers in the same shape
    as the request.
  - Operations about the multiplexer's own resources go to the holder over
    the socket it already keeps open, in the JSON lines it already speaks.
    The holder answers with the state of the operation.
  - Operations about the editor's own resources go into the editor's
    mailbox in the workspace engine. The editor takes its mail when it
    wakes on an event, and writes the result back into the engine. There
    is no daemon, no listener thread and no timer anywhere in this path.

* Conflicts and freshness
# what happens when both programs write at once, and when one is behind.
  - One writer at a time on the store: the second writer waits for the
    lock, so the last write wins whole and no field is half written.
  - The two programs never write each other's part. The engine's record of
    an editor buffer is a report of what the editor said, and the editor's
    own state is never rebuilt from that report.
  - A client that holds a version older than the store's version is told
    so, and refreshes. It never writes over a newer state on the strength
    of an old copy.
  - An operation that names a target the owner no longer has is failed
    with that reason, and never retried silently against another target.

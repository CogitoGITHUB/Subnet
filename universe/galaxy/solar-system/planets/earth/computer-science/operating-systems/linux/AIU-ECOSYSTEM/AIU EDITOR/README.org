* Paused: the terminal multiplexer comes first (2026-10-21)

The owner switched the priority on 2026-10-21. The editor's
implementation stops here; the =../AIU TERMINAL MULTIPLEXER/= is built
and verified first, because the complete workflow needs it and it is the
foundation under the editor.

Why: the editor is the program a human looks at, and the work it starts
must outlive it. An OpenCode server, a pm install that takes minutes and
an editor session all have to keep running while the human does
something else, and all three have to be attachable again afterwards.
The multiplexer is that: persistent sessions, a process lifecycle, and
attach/detach.

How the editor plugs in:
- the editor's own session runs in a multiplexer session, so the editor
  can be detached and re-attached without losing the session;
- the agent's pane is a multiplexer pane beside the editor's, and the
  agent keeps running when the editor is detached (TODO item 18);
- a long =pm= run started from the editor keeps running in its own
  session, and its event feed is read where the editor's own output is.

* What it is

AIU EDITOR is a general editor first: plain text, keyboard driven, no
daemon, no legacy baggage. It grows out of the neomacs work, and it
hosts AIU-NOTATION later as one pluggable engine behind a contract
boundary, never a dependency.

The program has two halves:

  - the Rust crate under =editor/= — the hot path: the text state, the
    journal, and the wire.
  - the Racket package under =editor/src/= — the meaning side: the
    command table, the routing, the narration, the error records.

They meet in one place, the =join/= area, and the wire between them is
one line of JSON each way.

* Build

  cargo build --manifest-path editor/Cargo.toml --target-dir /tmp/editor-target

The binary lands at =/tmp/editor-target/debug/hot-path=. Nothing is
written inside the tree; the build leaves =editor/Cargo.lock= behind,
so delete it:

  rm -f editor/Cargo.lock

* Run a session

  cd "<the AIU EDITOR directory>"
  racket editor/src/entry/cli.rkt edit FILE

The path must be RELATIVE: the project directory holds a space, and
racket splits a path that holds one.

The session reads one command per line from the standard input and
prints every answer in the one printer. The commands are:

  insert TEXT   put the text at the end of the buffer
  type TEXT     put the text where the cursor stands
  save          write the buffer to the file and empty the journal
  show          answer the text as it stands
  journal       answer the journal's records
  replay        rebuild the state and answer what is waiting
  move-up       move the cursor up a line
  move-down     move the cursor down a line
  move-left     move the cursor left a character
  move-right    move the cursor right a character
  delete        take one character out, before the cursor
  select        turn the selection on where the cursor stands
  send          send what is selected to the agent
  help          answer the names in the table
  quit          end the session

A real run:

  (ev-open the editor editing /tmp/readme-demo.txt 2026-10-20T08:21:56Z ...)
  bytes=22 file=/tmp/readme-demo.txt lines=1 pending=0
  bytes=30 lines=1 pending=1
  count=1 records=insert one line
  bytes=30 file=/tmp/readme-demo.txt lines=1 pending=0
  bytes=30 lines=1 text=hello from the read meone line
  bye

The numbers are: the bytes and the lines of the text, and =pending= — the
records in the journal, the edits that are not saved yet.

The **cursor** is a point in the text, and it moves: =move-left= and
=move-right= a character, =move-up= and =move-down= a line, and =type=
puts text where it stands. A session that typed at the cursor:

  type hello world
  move-left
  move-left
  type X

leaves =hello worXld= — the X landed where the cursor stood. The
journal records the place of every edit (=insert-at 14 and the second=),
so the state comes back exactly after a kill.

* The journal, and what a kill costs

The state between two commands is the file plus the journal: the saved
text lives in the file, the unsaved work lives in the journal. So a
crash, a kill or a closed terminal costs nothing.

The journal sits beside the state, one file per edited file:

  ~/.local/state/aiu-editor/journal/<name>-<key>.journal

A =save= writes the file and empties the journal. A session that is
killed with =kill -9= mid-edit leaves the edit in the journal, and the
next session on the same file brings the state back exactly.

* The routing: which layer sees a key first

The keyboard layer owns the routes, and the shape is the contract's: the
focused program sees a key first, then the editor's own layers, and the
multiplexer's reserved prefix applies everywhere.

  racket editor/src/entry/cli.rkt routes

prints the walk — one line per key, the layer that saw it and what it
meant there:

  layer: normal  program claims: none  reserved prefix: C-b
  C-b -> multiplexer -
  C-s -> editor save
  C-q -> editor quit
  C-l -> editor show
  C-h -> editor help

=C-b= is the reserved prefix: the multiplexer keeps it for its own
actions, it applies everywhere, and no layer of the editor may bind it.
The choice and its reason are in =decisions/reserved-prefix.org=.

The tables are data, not code: =editor/src/routes/keymaps.rkt= holds the
layers and their keys, and a route names a command from the command
table, never a function. A key is named the way the terminal names it:
=C-= for control, =M-= for alt, =S-= for shift, and a word for a named
key — escape, return, tab, space, backspace, delete, up, down, left,
right, home, end, pageup, pagedown.

* The tasks: declare, list, run, sequence

A task is a plain function on the meaning side: it takes the session and
the string arguments, and answers one line. Its doc line is the comment
block above its own definition, so the list and the help come from the
source and never from a second list.

  racket editor/src/entry/cli.rkt tasks

lists the table:

  insert — insert puts the words into the buffer and journals the edit. In the dry-run scope it prints what it would do and changes nothing.
  say — say prints the words it was given as one line, and changes nothing.

and a task runs against a file:

  racket editor/src/entry/cli.rkt task FILE NAME WORDS...

  racket editor/src/entry/cli.rkt task /tmp/tasks-demo.txt say hello the task runner
  hello the task runner

A =--= between two runs makes a sequence, and the runs go in the order
they were given:

  racket editor/src/entry/cli.rkt task FILE say first run -- insert a real line -- say second run
  first run
  bytes=41 lines=1 pending=1
  second run

=--dry-run= opens the scope where a task that acts prints what it would
do and changes nothing — the file and the journal stay untouched:

  racket editor/src/entry/cli.rkt task --dry-run FILE insert a line that must not land
  would insert: a line that must not land

A name the table does not hold is refused by name, never guessed at:
=there is no task named nosuchtask; ask for one of: insert, say=.

* The dashboard: the placeable pieces

The dashboard is the status and the context display. The placement is
**data**: a piece names an edge, a width and an order, so any piece can
go on any edge and several pieces can share one.

  racket editor/src/entry/cli.rkt dashboard FILE

draws the screen, one line per row:

  /tmp/tasks-demo.txt  1 lines  41 bytes  1 pending
  layer normal  agent idle -
  normal C-s -> save
  normal C-q -> quit
  normal C-l -> show
  normal C-h -> help

A piece is never cut: a piece whose text needs more room than its size
says gets the room it needs, so the same piece fits any edge. The same
piece was placed on all five edges — top, bottom, left, right and
floating — and every one of them put it where it was asked.

The meaning is Racket and the drawing is Rust; the two meet in the join
area. The gate's eighth stage, `dashboard-check.rkt`, checks that every
piece of the placeable piece list is really drawn, and it fails on a
piece welded to an edge the drawing does not know.

* The keyboard: the bytes of a key become its name

The keyboard is split the way D-007 says: the **decoding is Rust** (the
input area) and the **keymaps and the meaning stay in Racket** (the
routes area).

  racket editor/src/entry/cli.rkt keys normal 13 11 1b5b41 61 1b

answers the name of each key, the layer that saw it and the command it
runs:

  C-s -> normal save
  C-q -> normal quit
  up -> unclaimed -
  a -> unclaimed -
  escape -> unclaimed -

The bytes are given as hex, because a key may be any byte at all. The
hot path also answers the way back — how a key name is spelled — and the
gate's `key-check.rkt` stage walks every key of the keymaps round: the
name that comes back must be the name that went in.

The kitty keyboard protocol is **adopted, not invented**: the flags that
ask the terminal to report the escape codes it would otherwise swallow
are the protocol's own, and the reader uses no timer of its own. A lone
escape is the escape key, and the next byte decides it.

* The keyboard: plain keys, the trigger, the three modes

**No modifier at all.** The editor binds no escape, no meta, no alt and
no control key. Every key it takes is a key a person can press on its
own: a letter, a digit, space, return, tab, backspace, an arrow or a
function key. The reason is the owner's: the editor is driven from a
phone, and a phone keyboard has none of those keys on it.

**The trigger is space.** A trigger starts a sequence: the trigger and
the key after it are the command. The trigger pressed twice is the mode
change, so the mode changes with a *double space* and never with a
modifier.

**Three modes**, and they are named after what they are for:

| Mode | What it is | The trigger |
|---|---|---|
| =visual= | the general mode: the commands live here | =space= |
| =write= | the text mode: the keys are text | =tab= |
| =select= | the selected text is what the commands act on | =space= |

The write mode is the one place the trigger is not the space, because
there a space is a typed space. Its trigger is the tab — the one plain
key that is not text — and a double tab is the way back to the visual
mode.

What the keys do in the visual mode:

  space space   the mode change: to the write mode
  space w       the write mode
  space v       the select mode
  space s       save
  space q       quit
  space l       show the state of the file
  space ?       help
  space g       send what is selected to the agent
  up down left right   move the point
  backspace     delete

and in the write mode the keys are the text you type, with =tab s= to
save, =tab q= to quit and =tab v= to go back to the visual mode.

The tables are data, in =editor/src/routes/keymaps.rkt=, so what the
editor does with a key can be read without reading a function. The
gate's =key-check= stage asks the hot path how each key is spelled and
then what those bytes are: the name that comes back must be the name
that went in, so the decoder and the keymaps can never drift apart.

* The live session: the keys from the terminal

When the input is a terminal the editor is the real editor: the keys are
read one at a time, and each one is routed and run. When the input is a
pipe it stays the scripted session — one command per line — so every
proof that drives the editor with a pipe keeps working.

  racket editor/src/entry/cli.rkt edit FILE

The terminal is put in raw mode, so a key arrives without a return, and
**the settings that were found are saved first**: the terminal is given
back exactly as it was found, even when the editor was killed (the next
run gives it back before it goes raw again).

There is **no timer anywhere**. A read waits for the next byte, and a
key that is the start of a sequence waits for the next key — the next key
is an action, never a clock.

A real run, driven under a pseudo-terminal on the phone:

  bytes=0 file=/tmp/live-demo.txt lines=1 pending=0
  layer: write
  at=0 bytes=1 lines=1 pending=1
  at=1 bytes=2 lines=1 pending=2
  at=2 bytes=3 lines=1 pending=3
  at=3 bytes=4 lines=1 pending=4
  at=4 bytes=5 lines=1 pending=5
  layer: visual
  bytes=5 file=/tmp/live-demo.txt lines=1 pending=0
  bye

and the file held `hello` afterwards. A key that means nothing to
anybody is said out loud: `no key is bound to s`.

* The dev mode: work mode, the bake, the last good

The program runs in one of two modes, and the mode is the owner's
choice, read **once at the start** — there is no watcher, no poll and no
timer anywhere in it.

**The work mode** loads the config *live from the source*: the tables
are read at every start, so an edit to the source is seen at the next
start.

**The bake** makes the config into first-class defaults in a generated
module, so the baked program carries them inside it and needs no user
config at startup.

  racket editor/src/entry/cli.rkt bake

bakes, checks the result, and keeps it only when the check says yes:

  started in 3 ms, work mode, the config from the source tree
  baked: /root/home/shape/.local/state/aiu-editor/baked/keymaps.rkt
  the bake is good and is now the last good: …/baked/keymaps.rkt

**A bake that is not good never ships** — the last good stays the last
good, and the bad one is kept beside it to look at. That was proved on a
copy with the bake planted broken:

  the bake is NOT good; the last good stays: …/baked/keymaps.rkt

**The measured start** is printed with the first answer, and it is
information, not a gate:

  started in 3 ms, work mode, the config from the source tree
  started in 101 ms, baked mode, the config from …/baked/keymaps.rkt

The baked mode is chosen with `AIU_EDITOR_MODE=baked` in the
environment; anything else is the work mode.

* The send: the one action to an agent

The editor's one action is to build a bundle and call the boundary. The
bundle carries the contract's shape and **no agent-specific key and no
secret** — the adapter translates, and the program never learns which
agent answers.

  racket editor/src/entry/cli.rkt send FILE TARGET WHY...

  boundary: 1  program: aiu-editor  project: aiu-ecosystem  target: opencode
  why: checking the send shape
  position: 0
  selection:
  the send was refused: the agent is not attached — attach an agent first: the agent boundary is the one way to reach one

The **why is mandatory**: a send without a reason is refused, because a
send nobody can explain is a send that cannot be audited.

The adapter is the boundary one way — open or attach a session, send a
bundle, subscribe to the events, answer a permission ask, cancel, end —
and it reports the two pins: the boundary version it implements and the
agent version it was verified against. There is **no silent downgrade**:
what the agent cannot do today, the adapter refuses *by name*.

The boundary is one-sided until an agent is attached, and it says so
rather than pretending.

* The checkpoint, the rollback and the stop switch

A checkpoint is made **before an agent acts** — that is the whole point
of it. The files are added **one by one**, never a blanket add, and the
commit's note names the files that were *not* tracked, so nothing is
lost silently.

  racket editor/src/entry/cli.rkt checkpoint TREE WHY...
  racket editor/src/entry/cli.rkt rollback TREE COMMIT

The rollback puts the tree back and never guesses: a commit that is not
there is refused by name. Proved on a copy of a tree — the agent
changed the file, and the rollback put it back:

  checkpoint: aab5c83
  the tree is back at aab5c83

**A send makes its own checkpoint first**, so no bundle ever leaves
without one — the key and the command line do the same thing, because
both run the same one command.

The **stop switch** is coarse (D-010): it stops every agent session for
this project, and there is no per-session and no per-agent toggle. It is
a file in the state directory, and the adapter asks it on every call —
a call is an action, and nothing polls in a loop.

  racket editor/src/entry/cli.rkt stop stop    # throw it
  racket editor/src/entry/cli.rkt stop start   # clear it

* The plugin system: the editor asks pm, it never installs

A plugin is a package with a manifest. pm owns the package; the editor
owns how it talks to it, and the editor NEVER installs anything by
itself: it asks pm, and pm's rule is the editor's rule (reading is
free, changing the disk needs the human's =--confirm=).

  - =editor/src/notation/seam.rkt= — the calls the editor makes across
    the boundary: =describe=, =read-file=, =insert-text=, =save-file=.
    One JSON request and one JSON answer, both through files, so no
    session crosses the boundary.
  - =editor/src/notation/manifest.rkt= — what the editor knows about one
    plugin: name, version, the pm package, the spec, the command that
    starts it, the calls it provides. A manifest that misses a field is
    refused, and the field is named.
  - =editor/src/notation/pm.rkt= — the pm seam: =pm apply SPEC --confirm=
    only with the human's word, =pm verify VAULT LOCKFILE NAME= is free
    to read. pm's path comes from =AIU_PM_CLI=, or it is found by
    walking up the tree.
  - =editor/src/notation/loader.rkt= — loading a plugin. One that is not
    installed is refused BY NAME; one that fails to load never takes
    the editor down; a child that hangs is bounded so the editor does
    not hang with it.

The verbs: =plugin= (what is there, and what pm says), =plugin-register=,
=plugin-install=, =plugin-call=. The gate stage
=gate/plugin-check.rkt= proves the five things: a registered plugin
answers a seam call, a plugin that is not registered is refused by
name, a call the editor does not make is refused, the editor runs with
the plugin absent, and the editor never installs anything without the
human's word.

* The gate

  nu gate/check.nu

Ten stages, and a green run ends:

  light gate: green, 10 stages ran

  paren-check     every Racket file reads

  one-way         a require may point downward only
  security-gate   every security rule answers as it says

* The area law

The areas, lowest first:

  errors  narration  machine  security  join  devloop  journal  buffer
  notation  commands  routes  input  drawing  models  dashboard  send
  picker  checkpoint  audit  entry

=errors= is the floor and =entry= the ceiling, and a require may point
DOWNWARD only. Rust owns the hot path — =input/=, =drawing/=, =journal/=
and the buffer's text; Racket owns the meaning side — commands, routes,
models, rules and config. The seam is =join/=, and the one-way lint and
the language-split lint keep every other area clean.

  editor/src/narration/   the events, the voice, the wait door, the printer

  editor/src/journal/     the record of every edit, and the replay
  editor/src/buffer/      the text state: bytes, lines, offsets

The wire between the two halves is one line of JSON each way, and it
travels through a PAIR OF FILES — one for the request and one for the
answer. That is a fact of this Racket build and not a choice:
=racket/system= hands a child =/dev/null= for every stream that is not a
file stream. The decision is D-008 in the root DECISIONS.org.

* The agent: the boundary is real

  racket editor/src/entry/cli.rkt send FILE TARGET WHY...

opens a session with the agent, makes the checkpoint FIRST, hands the
bundle over, and answers the whole truth of the send: the bundle as it
went, what the agent said, the events that came back, and the
permission asks that wait for the human.

  racket editor/src/entry/cli.rkt agent
  racket editor/src/entry/cli.rkt permit once REQUEST-ID

The seam is OpenCode's headless server on the loopback, and the address
and the password come from the environment: =AIU_AGENT_URL=,
=AIU_AGENT_USER=, =AIU_AGENT_PASSWORD=, =AIU_AGENT_DIRECTORY=. The
server prints a fresh password when it starts.

The session is opened with every mutating action at =ask=, so the
agent's write comes back as a permission ask and nothing lands until
the human answers. The approval is never inferred.

* What is not there yet

    another project (its item 11).
  - pm itself does not run on this phone: its Racket package database

    installs nothing. That break is pm's to fix.
  - The send's turn is proved against a local stub agent, not against the
    live agent server: a real turn against the OpenCode host on this
    phone takes the host down with it, so the live proof is the one in
    =research/opencode-round-trip.org= and the standing proof is the
    gate stage =send-check=, which speaks the same wire.
  - The second agent adapter was skipped by the owner, so one adapter
    stands.
  - The root D-number for the reserved prefix is still owed: the root
    decision log is read-only from this project.
  - Nothing is long-lived. Every command is a one-shot call to the hot
    path, and the state lives in the file and the journal.

* Rules for anyone working here

  - Register a name in =plan/package-tree.org= before you use it.
  - One file, one job. Every file opens with a header comment that says
    what it is; every top-level definition has a comment line directly
    above it. The comment-lint stage checks this.
  - A require may point downward only.
  - Commit with explicit relative paths. Never =git add -A=.
  - Nothing writes outside =/tmp= and the state directory.
  - No test files in the tree (root DECISIONS.org D-001). A check that
    proves something is a stage of the gate, and a check that tries to
    fail is proved on a copy in =/tmp=.
  - Never weaken a check. A check that cannot fail is not a check.

#+TITLE: Editor hand-off — AIU NOTATION
# One job: what the notation engine offers the editor today, in plain words,
# with the real names, the real shapes and the real numbers.
# Written 2026-10-19 from the code and from captured output only. Nothing here
# is a plan; everything here was run.

* What the editor talks to

There are two sides, and they speak different shapes.

**The Rust engine** — one binary, =/tmp/notation-target/debug/notation=, with
four commands. It reads a =.aiu= page and knows nothing about the editor.

| command | input | output | exit |
| - | - | - | - |
| =notation parse FILE= | a .aiu page | the parse tree document on stdout, =parse-ms: N= on stderr | 0 |
| =notation render FILE= | a .aiu page | the plain render: the content, with the marks and the declaration lines gone | 0 |
| =notation render-rich FILE= | a .aiu page | the rich render: the same content drawn with unicode | 0 |
| =notation roundtrip FILE= | a .aiu page | =roundtrip: identical (N bytes)=, or =not identical= | 0 or 1 |

A real run on =syntax/example.aiu=:
```
/tmp/notation-target/debug/notation roundtrip syntax/example.aiu
roundtrip: identical (564 bytes)
```
A page the engine cannot read exits 2 and says why:
=notation: cannot read X: Y=.

**The Racket side** — =notation/src/entry/cli.rkt=, with the commands
=check=, =literate=, =send=, =json= and =from-json=.
* =check= reads a PARSE TREE DOCUMENT, not a .aiu page. The Rust =parse= makes
  that document; =tools/aiu.nu check= does both steps in order.
* =json= reads a .aiu page and prints its JSON form.
* =from-json= reads a .json file and prints the .aiu page it holds.
* The exit codes are named: =exit-clean 0=, =exit-findings 1=, =exit-refused 2=.

**A path with a space cannot be handed to racket.** The project directory is
=AIU NOTATION= with a space in it, and racket splits a path argument on the
space. Every racket command must therefore be run from the project directory
with a RELATIVE path:
```
cd "<project dir>" && /root/home/shape/opt/racket-full/bin/racket notation/src/entry/cli.rkt check FILE
```

* The calls the surface offers now

The =surface= area is the door to the editor. It answers with an ANSWERS
DOCUMENT whose header is =NOTATION-SURFACE 1=.

| call | input | output |
| - | - | - |
| =surface-answers= | the model (from =read-outline=) | the answers document |
| =answers-document= | the answers | the document as text |
| =read-answers= | the document as text | the answers again |
| =answers-at= | the answers, an address | the answer for that address |
| =write-surface-document= | a target, the answers | the document written out |
| =notice-header= / =read-notices= | a notices document | the header =NOTATION-NOTICE 1= and the notices |

The notices document has this shape:
```
file "<path>"
notice <kind> "<what>" "<detail>"
error <kind> <line> "<what>" "<whatToDo>"
end
```
The notice kinds are =parsed= and =did-change=.

The model layer gives the editor the rest:
=read-outline= (the document into a tree), =address-of= / =address-of-at= /
=addresses=, =property-of= / =tags-of=, =heading-numbers= / =number-at= /
=heading-level-of=, =collect-findings= / =build-report=.

* The exact shape of a diagnostic

The Racket finding has six fields:
```
(struct finding (kind who line column what what-to-do) #:transparent)
```
and the kinds are: =unknown-element-name=, =tag-names-nothing=,
=property-no-value=, =link-no-target=, =parser-recovery=.

A real report line, captured:
```
ERR err-stray.aiu at line 4, column unknown: parser-recovery: the parser recovered from stray-text: text outside any named block; what to do: put the text inside a "<name> start" / "<name> end" block
```
The column says =unknown= because a parse tree document carries no page. If
the editor has the page, it can count the column itself.

The Rust error node in the parse tree document has this shape:
```
error <kind> <line> <offset> <openerLine> "<what>" "<whatToDo>"
```
A real one:
```
error unclosed-block 77 78 5 "block \"paragraph\" was opened at line 5 and never closed" "add its matching \"paragraph end\" line"
```
The six error names the engine produces: =stray-text=, =mismatched-end=,
=unclosed-block=, =unknown-block-name=, =missing-title=, =bad-heading-level=.
A =mismatched-end= names the block AND the line it was opened at.

* The completion lists

Block names (the Rust parser's list, =notation/src/parser/parser.rs=):
=title=, =paragraph=, =code=, =heading=, =table=, =header=, =row=.

Declaration keywords (the same file):
=tags=, =language=, =style=, =theme=, =color=, =format=, =font=, =level=,
=caption=, =column=, =cell=, =row-id=, =meta=.

A completion must insert the START line AND the matching END line, because a
block that opens and never closes is an error:
```
paragraph start
paragraph end
```
The keyword comes FIRST both times. =end paragraph= (keyword last) is the
RETIRED spelling: it closes nothing and is read as content.

The Racket register of block names holds only four — =title=, =paragraph=,
=code=, =heading= (=notation/src/elements/register.rkt=). The =table=,
=header= and =row= names are known to the Rust parser and are NOT yet in the
Racket register. That gap is named here so the editor does not expect the
Racket side to know them yet.

* The spans the editor may hide

The engine already decides what a line is, in one place
(=notation/src/rendering/strip.rs=): a block line (=<name> start= or
=<name> end=), a declaration line (=keyword: value= with a registered
keyword), a comment line (inside a =comment start= / =comment end= block), or
plain content.

The plain render HIDES the block lines, the declaration lines and the
comments and keeps the content. So the editor may hide the same spans and the
reader will not notice a difference:
* the END line of a block,
* the declaration lines,
* the comment blocks.

How the engine reports them: the block line is a part of the block's span
(the block runs from its start line to its end line), and the declaration
lines are the block's =decl= entries in the parse tree document. The rich
render shows the content and the marks: a title gets a =═= rule, a code
block a box, a paragraph two columns of indent per nesting level, and an
error node a =✗ line N= mark.

* How an address is named

There are TWO shapes today, and they do not match. This is a real finding,
not a plan.

* The model: =<name>:<name>@<line>= — for example =title:title@1=. An error
  node is =error:<kind>@<line>=.
* The surface answers: =<kind>/<n>= — for example ="title/1"=.

Captured from the same document:
```
addresses: (title:title@1 paragraph:paragraph@6)
surface-answers -> (answer "title/1" "title" 'title 1 0 66 0)
```
The editor must be told which one it is given. This is a request, below.

* The measured timings

Measured on the phone this was built on (2026-10-19):

| what | time |
| - | - |
| Rust parse, a 20-line page | =parse-ms: 0= |
| Rust parse, a 2000-line page | =parse-ms: 40= / =36= / =43= |
| The whole check, 20 lines | 18363 ms |
| The whole check, 2000 lines | 18773 ms |
| The Racket check alone, 20 lines | 18817 ms |
| The Racket check alone, 2000 lines | 17855 ms |
| =racket -n -e ''= (the machine waking up) | 479 / 1523 / 499 ms |
| Loading ONE module (=model/outline.rkt=) | 10977 ms |
| Loading the CLI (=entry/cli.rkt=) | 23367 ms |
| A cargo build | 12660 ms |

THE NUMBER THE EDITOR NEEDS: the check costs the SAME on 20 lines and on 2000
lines, so the cost is not the page — it is the MODULE LOAD. The Rust engine
parses a 2000-line page in about 40 ms; the Racket side pays 11 to 23 seconds
to wake up on this device. The checking work itself is fast.

* The join status

What exists:
* the Rust engine parses, renders, renders richly and round-trips a page;
* the model reads the engine's document and gives addresses, properties,
  headings with their computed numbers, and findings;
* the surface answers the editor with an answers document;
* the incremental reparse exists and works: an edit in the middle of a file
  rebuilds ONLY the changed element ("rebuilt: [21] / kept: [1..20, 22..41] /
  incremental agrees with full reparse: true").

What is missing:
* there is no long-lived engine process: every command is one shot;
* the Racket side costs 11-23 s to start on this device, so a per-keystroke
  call to it is not possible today;
* the editor itself does not exist.

Two ways to join, with the real numbers. NEITHER IS DECIDED HERE.
* **A — the editor asks the engine for everything.** The editor sends the
  page, the engine answers with the tree, the addresses and the render. The
  cost of a full parse is 0-40 ms, so this can run on every keystroke IF the
  engine is a long-lived process; today it is a one-shot binary, so each
  keystroke would pay the process start.
* **B — the editor keeps the tree and the engine sends only what changed.**
  The engine already has the slice reparse: only the changed element is
  rebuilt. The cost per edit is then smaller than a full parse, but the
  editor must hold the tree, and the tree is built by the Rust engine, so the
  editor needs a way to hold or to receive it.

* What is long-lived and what is one-shot today

One-shot today: the Rust binary (one process per command), the Racket CLI
(one process per command), every gate stage, and =tools/aiu.nu= (which runs
the binary and then the Racket CLI as two processes).

Long-lived: nothing. There is no daemon, no socket and no pipe.

* Known gaps

1. The Racket =check= command reads a PARSE TREE DOCUMENT, not a .aiu page.
   The binary makes that document; =tools/aiu.nu check= does both steps.
2. A path with a space cannot be handed to racket; every racket command needs
   a relative path from the project directory.
3. The seven security rules have NO caller yet. =literate/targets.rkt= and
   =generation/write.rkt= still raise their own refusals instead of calling
   =security/refuse.rkt=. The gate names this on every run.
4. The =link= keyword is not registered, and the =references= area holds no
   files. So a link cannot be checked and a link cannot be resolved.
5. The kit (the MCP server, the skill, the plugin) is not built.
6. A heading's NUMBER cannot be known from one node. The caller must compute
   the numbers for the whole tree once and pass them down:
   =notation::numbering::HeadingNumbers::of(&tree)=, then
   =render_node_rich(node, buffer, width, depth, &numbers)=. The signature of
   =render_node_rich= therefore takes the numbers as a fifth argument, and
   that is a change from before the heading keyword.
7. Two address shapes exist (the model's =name:name@line= and the surface's
   =kind/n=). See the request below.

* Requests to the editor and to the contract

Written as requests. No contract file is touched by this document.

1. **One address shape.** The editor would rather have ONE way to name a
   place in a page. The model says =title:title@1=; the surface says
   ="title/1"=. Please say which one the editor should use, and whether the
   other one may be changed to match.
2. **A long-lived engine process.** The Racket side costs 11-23 s to start on
   a phone. If the editor is to use the surface, the engine needs a way to
   stay alive (a socket, a pipe, or a server command) so that the editor
   pays the start once. This is a request about the join, not a decision.
3. **The answer to "what may the editor hide?" is now written down** (the end
   lines, the declaration lines, the comment blocks) and the engine's own
   plain render already hides them. If the contract has a rule about hidden
   spans, this is the text to compare it with.
4. **A completion must insert the end line with the start line.** The engine
   reports an unclosed block as an error, so a completion that inserts only
   the start line hands the user an error. The engine can hand the editor the
   matching end line if that is wanted.

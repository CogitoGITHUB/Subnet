#+TITLE: AI-sight files
# One job: the on-disk files that let an agent see state without asking: what they hold and who writes them
# Status: filled 2026-10-16; working draft until a program and an adapter both depend on it.

* What this freezes
# the exact thing every program and adapter must obey; if it is not frozen here, authors guess.
  The sight-file rule: every program publishes a small set of stable,
  machine-readable state files, so an agent reads state directly and
  never has to interrogate the program. Reading is free.

* Shape
# names and meanings only: the fields and what they promise. No code, no examples.
  - One file per subject; fixed key order; one object per line; the same
    envelope keys as structured records.
  - Written on the event that changes them — install, rollback, bake,
    session start — never on a timer; flushed per record.
  - A file that cannot be written yet simply does not exist; a reader
    treats absence as "no state", never inventing a default.
  - Sight files are the durable summary; the event feed is the live
    detail; neither replaces the other.
  - Each program names its own set; PM's set is listed in
    pm-integration/ai-sight-files.org.

* Who obeys it
# every program and adapter this applies to, named.
  Every program writes its own set; every adapter publishes session
  state — which agent, session id, the boundary version it implements.

* How it changes
# how this can change without breaking a running client; point at a D-number once one exists.
  New subjects are additive. A file's shape changes only with a contract
  version bump. Freeze condition: when a program and an adapter both
  depend on it; none yet.

* Open decisions
# options with a recommendation, or none yet.
  - The directory: recommendation — one sight directory per program
    under its state home, from the one scope seam.
  - Whether session transcripts count as sight — recommendation: no;
    transcripts are records, not summaries.
